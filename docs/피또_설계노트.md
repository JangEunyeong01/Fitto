# 피또 (Fitto) — 설계 노트

> 개인 프로젝트 · 1인 개발 · React Native (Expo) + Spring Boot

화면 하나를 만들 때마다 내린 판단과 그 이유를 기록한 문서입니다. 구현 결과보다 **왜 그렇게 했는지**에 초점을 둡니다.

---

## 1. 프로젝트 개요

**피또**는 칼로리·수분·운동·생리 주기를 한 곳에서 기록하는 건강 관리 앱입니다. 숫자를 나열하는 대신 물방울 캐릭터의 표정과 움직임으로 오늘 상태를 먼저 보여주는 것을 컨셉으로 잡았습니다.

| 축 | 이 문서에서 다루는 근거 |
|---|---|
| 디자인 → 개발 연결 | 디자인 핸드오프 문서의 값을 코드 토큰으로 옮기고, 출처를 코드에 남긴 구조 |
| 인터랙션 구현 | 제스처 기반 입력, 상태에 반응하는 캐릭터 애니메이션 |
| 구조 설계 | 상태 스키마 버전 마이그레이션, 목데이터와 실데이터의 경계 분리 |
| 앱·서버 설계 | API 명세를 먼저 쓰고 그 계약에 맞춰 양쪽을 구현 |
| 스코프 판단 | 플랫폼 제약을 우회하되 기술 부채와 교체 시점을 명시한 결정들 |

---

## 2. 기술 스택

**앱** — Expo 57 / React Native 0.86 / TypeScript(strict) / Zustand(persist) / React Navigation 7 / Reanimated 4 + Gesture Handler / react-native-svg

**서버** — Java 21 / Spring Boot 4 / Spring Data JPA / PostgreSQL / JWT

**웹에서 앱으로 전환한 이유**

초기에는 웹으로 시작했지만 사용 맥락이 맞지 않았습니다. 건강 기록은 하루에 여러 번, 짧게, 손에 들고 하는 일입니다. 브라우저를 열고 주소를 치는 단계가 매번 끼어들면 기록이 이어지지 않습니다.

전환하면서 디자인 핸드오프 문서는 그대로 살아남았고(3장), 화면 구성과 계산 규칙도 재사용했습니다. 실제로 버린 것은 웹 전용 레이아웃 코드였습니다.

Expo를 고른 이유는 확인 속도입니다. 네이티브 빌드 환경 없이 폰과 웹에서 동시에 확인됩니다. 대신 네이티브 모듈 제약을 받으므로, 걸음수 센서 연동처럼 제약에 걸리는 기능은 그 지점을 코드에 명시해두었습니다(9장).

---

## 3. 디자인 → 코드: 핸드오프 값을 옮기는 규칙

디자인 산출물의 값을 코드로 옮기면서 **옮겼다는 사실과 출처를 코드에 남기는 규칙**을 세웠습니다.

- `src/theme/tokens.ts` 첫 줄 — "design-source README 값 그대로 이식"
- `src/utils/goals.ts` 첫 줄 — "README '온보딩 — 목표 계산식'을 그대로 옮긴 것. 수치를 임의로 바꾸지 않는다"
- 개별 토큰에도 출처 주석 — `periodBadgeGradient`에 "README: lavender .9 → peach .75"
- README에 값이 없어 **직접 판단한 부분은 그렇다고 명시** — `overlay.sheetBackdrop`에 "README에 값이 없어 튜토리얼 딤과 같은 색을 옅게 썼다"

**왜 이렇게 했는가**

디자인과 구현이 달라 보일 때, 그것이 *구현 실수*인지 *의도적 판단*인지 코드만 봐서는 알 수 없습니다. 출처가 남아 있으면 "핸드오프 값이니 디자인을 확인해야 한다"와 "값이 없어 내가 정한 것이니 바꿔도 된다"가 구분됩니다. 시간이 지나 직접 짠 코드를 다시 볼 때 특히 필요했습니다.

**파생 값은 계산해서 쓴다**

`alpha()` 헬퍼로 원본 토큰에서 투명도를 계산합니다. 반투명 색을 별도 상수로 박아두지 않아, 브랜드 색이 바뀌면 파생 색이 함께 따라옵니다.

**그 다음 단계 — 색을 팔레트와 역할로 나눴다**

핸드오프 값을 옮긴 토큰은 **팔레트만 있고 역할이 없었습니다.** `brand.blue` 하나가 버튼 면·링크 글씨·선택 테두리·차트에 동시에 쓰여서, 버튼 글씨 대비를 올리려고 값을 바꾸면 차트와 게이지까지 전부 바뀌는 구조였습니다. 실제로 재보니 파스텔 버튼 위 흰 글씨가 1.9:1, 보조 글씨가 2.4:1로 둘 다 기준(4.5:1)에 못 미쳤습니다.

초기 기획을 다시 열어보니 색마다 **쓰는 곳**이 적혀 있었습니다(Primary = 버튼·링크·스위치…). 방향은 맞았고, 한 색이 면과 글씨를 같이 맡은 게 문제였습니다.

| 층 | 예 | 쓰는 곳 |
|---|---|---|
| 팔레트 `brand` | `blue #89C4E1` | 면·차트·캐릭터 |
| 역할 `ThemeColors` | `textSecondary`, `textOnPrimary`, `borderInput` | 화면 코드는 이것만 쓴다 |

| 조합 | 전 | 후 |
|---|---|---|
| 보조 글씨 | 2.4:1 | 4.7:1 (216곳) |
| 주 버튼 글씨 | 흰색 1.9:1 | 짙은 남색 6.8:1 — 파스텔 면은 그대로 |
| 입력칸 테두리 | 유리 테두리 ~1:1 | 3.2:1 |

버튼을 진한 파랑으로 바꾸는 안도 계산했지만, 그러면 버튼만 파스텔 인상에서 튀어나옵니다. 면은 두고 글씨를 바꾸는 쪽을 골랐습니다.

키 이름을 `sub` → `textSecondary`처럼 **바꿔서** 옮겼습니다. 값만 바꿨다면 빠뜨린 곳이 조용히 남았을 텐데, 이름이 바뀌니 놓친 자리가 전부 타입 오류로 드러났습니다. 팔레트는 다시 잡을 예정이라, 그때는 역할 이름은 그대로 두고 값만 바꾸면 됩니다.

**그 다음 — 화면 전체 시안으로 다시 잡았습니다**

대비는 맞췄는데 화면이 여전히 시끄러웠습니다. 한 화면에 그라데이션 버튼이 둘셋, 줄마다 테두리 박스, 아이콘마다 색 칸이 있어서 **무엇을 눌러야 하는지가 흐렸습니다.** 화면 전체 시안(보드 42장 + 공통 규칙 28개)을 만들어 "기록은 가볍게, 확인은 한눈에"로 방향을 정했습니다 — 하루에도 여러 번 열어 물 한 잔을 남기는 앱이라, 누를 것은 화면당 하나만 칠하고 나머지는 글씨로 물렸습니다.

| 전 | 후 |
|---|---|
| 그라데이션 칠한 버튼 여러 개 | 단색 칠한 버튼 **하나**, 나머지는 글씨 버튼 |
| 줄마다 박스 | 카드 한 장 안 얇은 선 |
| 삭제 전 확인창 | 바로 지우고 토스트에서 "실행 취소"(5초) |
| 모든 탭에 시간대 색 | 홈에만 |

옮기는 방식은 역할 토큰 때와 같습니다. 부품(버튼·칩·입력칸·세그먼트)을 먼저 바꾸고 화면은 그 부품을 가져다 쓰게 해서, **화면 파일에는 색·크기 숫자가 거의 새로 생기지 않았습니다.** 시안이 기준과 부딪히는 곳은 기준을 따르고 이유를 남겼습니다 — 목록 삭제 버튼은 시안의 폭 28 대신 44(누르는 영역), 선택 칩 테두리는 시안의 파스텔 대신 3:1을 넘는 색, 입력칸은 면만 두는 시안에 "입력하는 동안만 아래 선"을 더했습니다(포커스를 색 말고 모양으로도).

새 부품은 쓰는 곳이 둘 이상일 때만 만들었습니다. 시트 공통 틀, 가운데 알림창 틀, 인증 코드 6칸, 설정 목록 줄, 생년월일 칸 다섯입니다. 한 곳에서만 쓰는 모양(테마 메뉴, 재료 한 줄 입력)은 그 화면 안에 둡니다. 거꾸로 이미 있던 부품을 합치기도 했습니다 — 온보딩의 목록 줄·태그 고르기와 프로필 시트의 것이 같은 모양이라, 프로필 시트가 온보딩 부품을 그대로 가져다 씁니다.

**홈 카드 순서는 길게 눌러 끌기로 바꿨습니다.** 위·아래 버튼으로는 맨 아래 카드를 맨 위로 올리려면 여섯 번 눌러야 했습니다. 끌기 라이브러리를 새로 들일지 고민했는데, 물 카드 드래그에 쓰던 제스처 도구(gesture-handler + reanimated)로 충분해서 의존성을 늘리지 않았습니다. 손가락 위치처럼 초당 수십 번 바뀌는 값은 애니메이션 쪽 값(shared value)으로, "몇 번째 칸에 놓일지"처럼 가끔 바뀌는 값만 화면 상태로 둬서 끄는 동안 화면을 다시 그리지 않습니다. 끌기를 못 쓰는 사람(스크린리더)을 위해 줄마다 "위로·아래로 옮기기" 동작을 남겼습니다.

## 4. 기획 → 코드 구조: 캐릭터 성격 3종

마스코트의 성격 3종(친근형 / 엄격형 / 차분형)이라는 기획을, 화면 곳곳에 흩어진 문구가 아니라 **하나의 문구 리소스 테이블**로 구현했습니다.

- `src/copy/persona.ts` — 13개 상황 × 3개 성격의 문구를 함수 테이블로 관리(기기 알림 문구 4개 포함)
- 규칙: 하드코딩 카피 대신 이 테이블을 통해서만 참조
- 값이 들어가는 문구는 함수로 — `(v: { remainKcal }) => ...`

함수로 둔 덕분에 성격별로 **문장 구조 자체가 달라질 수 있습니다.** 같은 상황에서 친근형은 남은 물 양을 먼저 말하고 엄격형은 초과한 칼로리를 먼저 말합니다. 말투만 바꾸는 치환이었다면 문자열 테이블로 충분했겠지만, 성격마다 **무엇을 먼저 말할지**가 달라야 한다고 봤기 때문에 함수 테이블이 됐습니다.

**홈 브리핑 — 말할 것과 말하지 않을 것을 규칙으로 고정했습니다**

홈 상단에서 로고 아래 인사와 오늘 한 줄을 보여줍니다(`src/copy/briefing.ts`). 화면 코드에는 조건문을 두지 않고, 순수 함수 하나가 기록을 받아 세 줄(인사 / 기본 / 이벤트)을 돌려줍니다.

기본 줄은 **수분과 칼로리만** 다룹니다. 처음에는 걸음 수까지 세 가지를 기본으로 두려 했는데, 목표가 사람마다 반대 방향이라는 점에서 걸렸습니다. 감량이 목표인 사람에게 맞는 문장이 증량이 목표인 사람에게는 반대로 읽히고, 무엇보다 **관절 질환이 있는 사람에게 "더 걸으세요"는 조언이 아니라 해**입니다. 프로필에 질환을 받아두고도 그걸 무시한 문구를 내보내는 셈이 됩니다. 걸음은 카드에서 숫자만 보여주고 브리핑에서는 빼기로 했습니다.

이벤트 줄은 **오늘 특별한 일이 있을 때만** 만듭니다. 우선순위는 생리 1일차 → 생리 예정(2일 전부터) → 많이 움직인 날(30분 또는 300kcal) → 물 목표 달성 → 3일 이상 연속 기록이고, 걸리는 게 없으면 `null`을 돌려줘서 화면이 빈 줄을 만들지 않습니다. 지적은 넣지 않았습니다 — 격려와 안내만 합니다.

분기가 많은데 화면에서는 그날 조건에 걸린 한 줄만 보입니다. 생리 1일차 문구가 제대로 뜨는지 눈으로 보려면 날짜를 바꿔가며 앱을 열어야 해서, `npm run check:copy`로 규칙을 대신 확인합니다(`scripts/check-briefing.mjs`, 매핑 점검과 같은 방식).

## 5. 상태 설계와 스키마 마이그레이션

`src/store/useAppStore.ts` — Zustand + AsyncStorage 영속화. 기기에 저장된 상태가 앱 업데이트 이후에도 깨지지 않도록 **버전 마이그레이션**을 두었습니다. 현재 v7입니다.

| 버전 | 이관 내용 |
|------|-----------|
| v2 | 홈 카드 기본 순서 변경. 사용자가 순서를 직접 바꾼 적이 없을 때만 새 순서로 옮김 |
| v3 | 한글 라벨 저장 → 코드값(`"당뇨"` → `diabetes`), 목록에 없는 직접 입력값은 `custom*` 배열로 분리 |
| v4 | 끼니·증상 코드화, 음식 양을 `"1공기 210g × 2"` 문자열 → 숫자 + 단위 |
| v5 | 앱 시작일 추가. 기존 사용자는 기록이 남은 가장 오래된 날짜로 채움 |
| v6 | 기록 ID를 UUID로 통일. 예전엔 `${Date.now()}` 형식으로 만들었는데, 서버가 UUID만 받아서(명세 0-2) 그대로 두면 이미 쌓인 기록이 영영 안 올라감 |
| v7 | 온보딩 끝 계정 선택 화면을 넣으면서, 이미 온보딩을 마친 사람은 "물어본 것으로" 처리. 안 그러면 잘 쓰던 사람이 앱을 열자마자 가입 화면을 봄 |

v2가 필요했던 이유가 이 설계의 요지입니다. 기본값을 바꾼다는 것은 **이미 그 값을 쓰고 있는 사용자가 있다**는 뜻이고, 그 사람이 직접 설정한 순서를 덮어쓰면 안 됩니다. 그래서 "이전 기본값 그대로일 때만" 이동시킵니다.

**마이그레이션에서 겪은 문제**

변환 함수가 예외를 던지면 persist가 복구를 **통째로 포기합니다.** 화면에는 기록이 전부 사라지고 앱이 초기화된 것처럼 보입니다. 저장본의 버전과 실제 구조가 어긋난 상태에서 이미 변환된 값을 다시 변환하려다 발생했습니다.

지금은 이미 변환된 형태가 들어와도 그대로 통과시키는 가드를 두었습니다. 마이그레이션은 한 번 깨지면 사용자가 되돌릴 방법이 없는 자리라 방어적으로 작성해야 한다고 판단했습니다.

**날짜별 기록 구조**

**버전을 올리지 않은 변경 — 나이 대신 생년월일**

나이를 숫자로 받던 걸 생년월일로 바꿨습니다. 나이는 해마다 바뀌는 값이라 받아두면 1년 뒤엔 틀려 있고, 생일 축하에 쓰던 월·일은 따로 받고 있어서 연도만 더 받으면 됐습니다. 나이는 생년월일이 바뀔 때 계산해 저장하고, 목표 칼로리 계산과 서버는 지금처럼 `age`를 씁니다 — 공식을 건드리지 않으니 앱·서버 계산이 어긋날 일이 없습니다.

이번엔 마이그레이션 버전을 올리지 않았습니다. 저장본을 불러올 때 **객체 필드는 기본값 위에 저장본을 얹는** 병합을 이미 해두어서, 새 필드(`birthYear`)는 기존 사용자에게 `null`로 자연스럽게 채워집니다. 대신 연도가 비어 있는 사람에게는 설정의 프로필 줄과 프로필 화면에 "태어난 연도를 넣어 주세요"를 띄우고, 채우면 사라집니다. 없는 연도를 나이에서 거꾸로 추정해 넣지 않은 건 **추정값을 사실처럼 저장하지 않는다**는 원칙 때문입니다. 서버에는 `birth_year` 열을 추가했고(`V3__birth_year.sql`), 생년월일 세 칸은 한 묶음으로 주고받습니다.

한계도 적어 둡니다. 나이를 저장 시점에 계산하므로, 생일이 지나도 다음에 프로필을 고치기 전까지는 한 살 어리게 남습니다. 목표 칼로리로 5kcal 남짓이라 두고, 코드에 적어 두었습니다.

**날짜별 기록 구조**

`dailyRecords`는 `"2026-09-17"` 형태의 날짜 키 맵입니다. 배열로 두면 날짜를 찾을 때마다 순회해야 하고, 같은 날짜 레코드가 둘 생길 여지가 있습니다. 조회 함수는 기록이 없는 날짜에 빈 레코드를 돌려주어, 호출부마다 null 체크를 반복하지 않게 했습니다.

## 7. 플랫폼 제약과 우회

원본 웹 프로토타입은 캐릭터의 5단계 상태를 CSS `filter`(grayscale / saturate / brightness)로 표현했지만, **React Native의 `Image`에는 CSS filter를 적용할 수 없습니다.**

선택한 해법 — 반투명 오버레이 3겹으로 근사:

| 원본 filter | 대체 |
|---|---|
| 채도 감소 | 회색 레이어 불투명도 `grayscale * 0.55` |
| 채도 증가 | 브랜드 블루 레이어 `(saturate - 1) * 0.28` |
| 밝기 | 흰색 레이어 `(brightness - 1) * 0.5` |

**중요한 건 그 다음입니다.** 코드에 "최종 5단계 일러스트가 준비되면 이미지 스왑으로 교체 권장"을 남기고, 오버레이 색 토큰에도 "이미지 스왑으로 바뀌면서 함께 제거된다"를 적었습니다.

근사치로 간 이유는 지금 필요한 것이 *정확한 색 변환*이 아니라 *단계가 구분되는 시각적 피드백*이었기 때문입니다. 다만 근사라는 사실과 더 나은 해법을 남기지 않으면, 나중에 이 코드를 보는 사람은 이게 최선인 줄 알고 그대로 둡니다. 1인 개발에서는 그 "나중에 보는 사람"이 대부분 자신입니다.

같은 맥락의 다른 사례:

- 반폭 카드에서 원본의 가로 배치(컵+컨트롤)가 45px로 찌그러져 세로 배치로 변경. 원본을 따르지 않기로 한 판단과 이유를 주석으로 남김
- 웹에서 `absoluteFill`에 width/height가 없어 이미지가 원본 크기(578×731)로 삐져나오는 문제를 크기 명시로 해결

## 8. 트러블슈팅

배포 전에 영역을 나눠 열세 번에 걸쳐 점검했습니다. 코드를 읽는 것으로는 절반이 안 잡혀서, **직접 공격해보고 DB를 열어 확인하는 방식**으로 진행했습니다.

| 영역 | 확인 방법 | 결과 |
|------|-----------|------|
| 시크릿 유출 | 커밋 이력·번들 전수 검색 | `.gitignore` 누락 1건 |
| 인증·비밀번호 | 응답 시간 측정, 계정 바꿔가며 시도 | 3건 |
| 토큰 | 위조 토큰 5종 제작, DB 상태 대조 | 3건 |
| 권한 | 두 계정으로 31가지 교차 접근 | 1건 |
| 입력 검증 | 29가지 잘못된 입력 | 4건 |
| XSS | 화면에 스크립트 주입 후 DOM 확인 | 0건 |
| CORS·CSRF | 다른 출처에서 요청, 폼 전송 흉내 | 1건 |
| API | 35개 엔드포인트 인증·권한 전수 | 1건 |
| 로그 | 이벤트 발생시키고 기록 확인 | 1건 |
| 배포 설정 | 프로파일·의존성·빌드 산출물 | 3건 |

숫자보다 중요한 건 **어떤 종류가 안 잡히는지**였습니다. 응답도 로그도 정상인데 DB만 다른 경우, 주석은 맞는데 설정이 안 읽히는 경우, 화면에 아무 증상이 없는데 기록이 서버에 안 올라가는 경우가 그랬습니다. 아래 사례들이 그것입니다.

### 온보딩 태그를 빠르게 두 번 누르면 앞선 선택이 사라지는 문제

- **증상** 태그 선택 화면에서 두 개를 빠르게 연속으로 누르면 먼저 누른 것이 선택 해제됨
- **원인** 선택 배열 전체를 인자로 받아 갱신하는 구조라, 리렌더 전에 두 번째 클릭이 들어오면 **갱신 전의 낡은 배열**을 기준으로 덮어씀
- **해결** `toggleObTag(key, value)` — 배열이 아니라 **바뀐 항목 하나만** 받고, 스토어 내부에서 항상 최신 상태를 기준으로 토글
- **파일** `src/store/useAppStore.ts`

### 한 DB에서는 통과하고 다른 DB에서는 테이블이 안 만들어진 문제

- **증상** Postgres에 실제 요청을 보내 가입·기록·조회를 모두 확인한 뒤, 같은 흐름을 H2로 돌리는 통합 테스트를 작성했더니 9개가 한꺼번에 실패
- **원인** 직접 입력 목록 테이블의 컬럼 이름이 `value`였다. Postgres에서는 쓸 수 있지만 **H2에서는 예약어**라 `create table`이 실패했다. Hibernate는 테이블 생성 실패를 경고로만 남기고 진행하기 때문에, 부팅은 정상이었고 `insert` 시점에야 `Table not found`로 드러났다
- **해결** 컬럼 이름을 `item`으로 변경. 같은 부류인 `@OrderColumn(name = "position")`도 `sort_order`로 함께 변경
- **남긴 것** 엔티티 주석에 왜 `value`를 못 쓰는지와 어떻게 발견했는지 기록

수동 확인만 했다면 "잘 된다"로 끝났을 문제다. 테스트 DB를 운영과 다르게 잡은 것이 오히려 **DB에 종속된 코드를 드러내는 장치**가 됐다.

### Spring Boot 4로 올리면서 겪은 것들

최신 정식 버전을 골랐더니 인터넷 예제가 대부분 3.x 기준이라 그대로 쓸 수 없는 지점이 반복해서 나왔다.

| 항목 | 3.x | 4.x |
|---|---|---|
| 웹 스타터 | `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| Jackson 패키지 | `com.fasterxml.jackson.databind` | `tools.jackson.databind` |
| MockMvc 자동설정 | `...test.autoconfigure.web.servlet` | `...webmvc.test.autoconfigure` |
| enum 직렬화 설정 | `spring.jackson.serialization.*` | `spring.jackson.datatype.enum.*` |

문제를 푼 방식은 매번 같았다 — 검색해서 나오는 답이 안 맞으면 **의존성 jar 안을 직접 열어 실제 클래스 경로를 확인**했다. 예제가 없는 버전을 쓸 때는 이 방법이 가장 빠르다.

### 운동 기록만 계속 500으로 실패한 문제

- **증상** 앱에서 기록한 물은 서버에 저장되는데 운동만 `500 INTERNAL_ERROR`. 재시도 5회 후 버려짐
- **원인** 앱이 만드는 기록 ID가 `${Date.now()}` 문자열이었다. 서버는 UUID만 받으므로(명세 0-2) 요청 본문을 읽는 단계에서 실패했다. 물은 ID 없이 날짜로만 저장하는 API라 영향이 없었다
- **왜 늦게 찾았나** 서버가 이 상황에 `500`을 주고 있었다. 500은 "서버가 깨졌다"는 뜻이라 서버 로그부터 뒤지게 만든다. 실제로는 보낸 쪽 잘못이었다
- **해결** 세 가지를 함께 고쳤다
  1. UUID v4 생성기를 만들고 ID 생성 지점 9곳 교체
  2. persist 마이그레이션(v6)으로 **이미 저장된 옛 ID도 변환** — 안 하면 기존 기록이 영영 안 올라간다
  3. 서버가 요청 본문을 못 읽는 경우를 `400`으로 응답하도록 수정
- **남긴 것** 3번이 핵심 수정이다. 클라이언트 잘못을 서버 오류로 감추면 원인이 엉뚱한 곳에서 찾아진다

### PATCH에서 "안 보낸 필드"와 "null"을 구분하지 못한 문제

- **증상** 프로필 수정 API에서 물 목표 직접 설정을 해제하는 규칙을 `waterGoal: null`로 정했는데, 서버에서 "필드를 안 보낸 경우"와 구분할 방법이 없었다
- **원인** JSON에는 "값이 없음"을 나타내는 방법이 `null` 하나뿐이다. Java DTO로 역직렬화하면 두 경우 모두 필드가 `null`이 된다. `Optional<Integer>`로 감싸 세 상태를 만들어보려 했지만, Jackson은 **필드가 아예 없어도 `Optional.empty()`를 만들어서** 결국 구분되지 않았다
- **위험** 이 상태로 `null = 지우기`를 유지하면, 앱이 실수로 빠뜨린 필드가 "지워라"로 해석돼 프로필이 지워진다
- **해결** 우회 구현(커스텀 Deserializer, 추가 라이브러리) 대신 **API 계약을 바꿨다.** `null`은 안전한 쪽(유지)으로 해석하고, 지우려는 의도는 `waterGoalCustom: false`라는 명시적 필드로 받는다. 이 필드는 이미 User 응답에 있던 것이라 새 개념도 아니다
- **남긴 것** 이 세 상태가 실제로 어떻게 동작하는지 확인하는 테스트. 처음 가정이 틀렸던 자리라 가정을 코드로 고정해두었다

### 저장된 데이터를 복구하다 앱이 초기화된 것처럼 보이는 문제

- **증상** 앱을 켜면 온보딩 화면부터 다시 시작. 저장소에는 기록이 그대로 남아 있음
- **원인** persist 마이그레이션 함수가 예외를 던지면 복구 전체를 포기하고 초기 상태로 시작. 이미 코드값으로 변환된 데이터를 다시 변환하려다 타입이 맞지 않아 예외 발생
- **해결** 변환 함수가 이미 변환된 형태를 받아도 그대로 통과시키도록 가드 추가
- **파일** `src/store/useAppStore.ts`

### 응답을 같게 맞췄는데도 가입 여부가 새어 나간 문제

배포 전 인증 쪽을 점검하다 찾았습니다.

- **증상** 로그인 실패 응답은 `INVALID_CREDENTIALS`로 통일돼 있었지만, 응답 시간이 갈렸다. 가입된 계정 ~95ms, 없는 계정 ~14ms
- **원인** 계정을 못 찾으면 비밀번호 비교를 건너뛰고 바로 실패 처리. BCrypt는 일부러 느린 함수(cost 10에서 약 100ms)라 그 차이가 그대로 드러났다. 메시지를 가려도 시간을 재면 어느 이메일이 가입돼 있는지 알 수 있다
- **해결** 계정이 없으면 어떤 비밀번호와도 일치하지 않는 더미 해시와 비교시켜 걸리는 시간을 맞춤. 실측 결과 양쪽 모두 90~110ms로 수렴
- **같이 고친 것** 실패 횟수 제한이 이메일 기준뿐이라, 이메일을 바꿔가며 흔한 비밀번호를 뿌리는 공격(password spraying)은 아무 제한에도 걸리지 않았다. 계정마다 카운터가 새로 시작하기 때문. IP 기준 제한(10분 30회)을 한 축 더 두고, 두 곳에 흩어져 있던 횟수 세는 코드를 `AttemptCounter` 하나로 합쳤다
- **파일** `server/.../auth/AuthService.java`, `LoginAttemptGuard.java`, `AttemptCounter.java`

응답 본문만 가리는 것으로는 부족하고 **처리 시간도 관찰 가능한 정보**라는 걸 실측으로 확인한 사례입니다.

### 토큰 탈취를 감지하고도 막지 못한 문제

- **증상** 이미 쓴 refreshToken이 다시 오면 401 `REFRESH_TOKEN_REUSED`가 나갔다. 코드대로면 그 사용자의 토큰이 전부 폐기돼야 하는데, 직전에 발급된 토큰으로 갱신하면 그대로 200이 떨어졌다
- **원인** 폐기 처리 뒤 곧바로 `ApiException`을 던지는데, 이게 RuntimeException이라 `@Transactional`에 롤백이 걸렸다. **폐기까지 같이 취소된 것.** DB를 보니 `revoked_at`이 전부 비어 있었다
- **해결** 폐기만 별도 트랜잭션(`REQUIRES_NEW`)으로 분리. 엔티티를 하나씩 불러 고치는 대신 벌크 update로 바꿈
- **파일** `server/.../auth/AuthService.java`, `RefreshTokenRepository.java`

응답과 로그만 보면 정상이라 코드 읽기로는 놓치기 쉬운 종류였습니다. **DB 상태를 직접 확인하고 나서야** 드러났습니다.

같은 점검에서 만료 토큰이 위조 토큰과 구분 없이 `UNAUTHORIZED`로 나가던 것도 고쳤습니다. 앱이 "갱신하면 되는 상태"를 알아야 해서 만료만 `TOKEN_EXPIRED`로 구분하고, 위조는 사유를 알려주지 않습니다.

점검에는 `alg=none`, 서명 없는 토큰, 다른 키로 서명한 토큰, refreshToken을 accessToken 자리에 넣는 경우까지 직접 만들어 넣어봤습니다.

### 앱의 입력 제한이 빠져서 기록이 사라지는 문제

- **증상** 없음. 화면에는 정상으로 보인다. 기기에는 기록이 남지만 서버에는 올라가지 않는다
- **원인** 앱 입력 여섯 곳에 길이 제한이 없었다. 서버가 허용하는 길이를 넘기면 400이 떨어지고, 전송 대기열이 5번 재시도한 뒤 그 작업을 버린다. 낙관적 업데이트라 화면은 이미 저장된 상태로 보인다
- **해결** 서버 제약과 같은 값으로 `maxLength`를 넣고, 레시피 재료의 그램수·칼로리 상한도 맞춤
- **파일** `src/screens/recipe/RecipeScreen.tsx`, `src/screens/settings/ProfileScreen.tsx`, `src/screens/onboarding/TagPicker.tsx`, `BasicInfoForm.tsx`

낙관적 업데이트는 성공을 먼저 보여주므로, **거절될 값을 애초에 만들 수 없게 하는 것**이 화면과 서버가 갈라지지 않는 유일한 방법입니다.

같은 점검에서 서버의 일괄 가져오기(명세 6장)에 제약이 하나도 없는 것도 찾았습니다. `@Valid`는 붙어 있었지만 안쪽 record에 제약이 없어 아무 일도 하지 않았습니다. 개별 API를 다 막아도 이 통로로 우회됩니다. 실제로 2만 건을 보내니 응답이 십수 분 동안 돌아오지 않았고, 배열 길이 상한을 넣은 뒤에는 1.4초에 400으로 끊깁니다.

### 내려받기가 토큰을 갱신하지 못해 동기화가 멈추는 문제

- **증상** 앱을 오래 뒤에 열면 서버 기록이 안 내려온다. 기록을 하나 만들면 그때부터 정상
- **원인** 401에서 토큰을 갱신하는 처리가 밀어올리기에만 있었다. 새로 기록한 게 없으면 대기열이 비어 밀어올리기가 돌지 않으므로 갱신할 기회 자체가 없었다. 내려받기는 오류를 조용히 삼켰다
- **해결** 내려받기도 401이면 한 번 갱신하고 다시 시도
- **파일** `src/sync/pull.ts`, `src/sync/syncEngine.ts`

네트워크 기록을 보고 찾았습니다. `/users/me`가 401을 반복하는데 `/auth/refresh`는 한 번도 불리지 않았습니다.

### 잘못 부른 요청이 전부 서버 잘못으로 보고되던 문제

- **증상** 없는 경로에 접근해도 500. 지원하지 않는 형식, 허용되지 않은 메서드, 쿼리 파라미터 형식 오류까지 일곱 가지가 모두 500
- **원인** `@ExceptionHandler(Exception.class)`가 스프링이 컨트롤러를 부르기 **전에** 던지는 표준 예외까지 전부 삼켰다. 요청은 정상적으로 거부되고 있어서 동작만 보면 문제가 없었다
- **해결** 400·404·405·415를 각각 잡고, 500에는 예상하지 못한 예외만 남김
- **파일** `server/.../common/error/GlobalExceptionHandler.java`

동작이 아니라 **상태 코드만 틀린 문제**라 기능 테스트로는 드러나지 않습니다. 그런데 운영에서는 세 가지가 나빠집니다. 보낸 쪽 잘못이 서버 잘못으로 보고되고, 로그가 ERROR 스택으로 뒤덮여 진짜 장애가 묻히고, 경로를 훑는 스캐너 하나로 5xx 알림이 울립니다.

CSRF 점검을 하다 찾았습니다. 브라우저 `<form>`은 사전 요청 없이 바로 전송되므로 CORS로는 막지 못합니다. 대신 폼이 쓸 수 있는 `Content-Type`이 세 가지뿐이고 서버가 JSON만 받아서 전부 거절되는데, 그 거절이 415가 아니라 500으로 나가고 있었습니다.

### 주석은 맞는데 설정이 읽히지 않던 문제

- **증상** 없음. 의도한 대로 동작하는 것처럼 보였다
- **원인** `flyway.enabled`와 `servlet.multipart`가 `spring:`이 아니라 `fitto:` 아래에 들어가 있었다. 스프링이 읽지 않는 키라 아무 효과가 없었는데, 개발 DB에 마이그레이션 이력이 없어서 결과만 보면 의도대로였다. **설정이 동작한 게 아니라 다른 이유로 안 돌고 있었던 것**
- **해결** `spring:` 아래로 옮김. 테스트용 설정 파일은 본 설정을 병합이 아니라 **대체**하므로 거기에도 따로 명시
- **파일** `server/src/main/resources/application.yaml`, `src/test/resources/application.yaml`

주석에 의도가 적혀 있어서 오히려 눈에 안 들어왔습니다. 읽는 사람은 "개발에서 꺼뒀구나" 하고 넘어갑니다. **의도와 결과가 우연히 맞는 상태**라 조건이 하나 바뀌면 그때 드러납니다.

**"다른 이유"는 배포 리허설에서 밝혀졌습니다.** 무료 인스턴스와 같은 조건(메모리 512MB, CPU 0.1개)으로 컨테이너를 띄우고 빈 DB에 운영 설정을 붙였더니, 스키마 검증이 첫 테이블부터 없다며 멈췄습니다. 로그에 Flyway가 한 줄도 없었습니다.

Spring Boot 4는 자동 설정을 기능별 모듈로 나눴습니다. `flyway-core`만 넣으면 라이브러리는 들어오지만 **부팅할 때 마이그레이션을 실행하는 자동 설정이 빠집니다.** 오류도 경고도 없습니다. `spring-boot-starter-flyway`로 바꾸자 `V1`이 적용되고 서버가 떴습니다.

개발에서 Flyway가 안 돈 건 설정 덕분이 아니라 **처음부터 연결이 안 돼 있어서**였습니다. 그리고 이번에 설정을 제자리로 옮겨둔 덕에, Flyway가 연결된 뒤에도 개발 서버는 기존 테이블 위에 마이그레이션을 돌리지 않습니다. 두 문제가 서로를 가리고 있었습니다.

로컬에서 서버를 몇 번을 띄워도 안 보이는 종류라, **운영과 같은 조건으로 한 번 띄워보는 것**이 배포 전 확인 중 가장 값이 컸습니다.

### 컨테이너를 교체할 때 처리 중이던 요청이 끊기던 문제

- **원인** `ENTRYPOINT ["sh", "-c", "java -jar app.jar"]`. `sh`가 PID 1이 되면 종료 신호(SIGTERM)가 java까지 전달되지 않는다
- **해결** `ENTRYPOINT ["java", "-jar", "app.jar"]`로 바꾸고 `server.shutdown: graceful`을 켬
- **파일** `server/Dockerfile`, `application-prod.yaml`

배포할 때마다 조용히 일어나는 종류라, 확인하려면 배포 동작을 따로 들여다봐야 합니다.

### 탈퇴에서 지울 표를 사람이 적으면 언젠가 샙니다

- **상황** 회원 탈퇴를 만들면서 DB를 세어보니 `user_id` 컬럼이 있는 표가 18개인데, 외래키로 `users`에 묶인 건 6개뿐이었다. `users` 한 줄만 지우면 나머지 12개 표의 식단·운동·생리 기록이 **주인 없이 남는다.** 오류가 나지 않아 화면상으로는 지워진 것처럼 보인다
- **판단** 운영 DB가 이미 떠 있어 연쇄 삭제를 DB에 맡기는 대신 코드에 명시했다. 대신 **목록을 사람이 관리하지 않게** 했다 — 테스트가 `information_schema`에서 `user_id` 컬럼을 가진 표를 직접 읽어, 탈퇴 전에는 전부 차 있고 후에는 전부 비었는지 확인한다. 표가 늘고 삭제 코드에 추가하는 걸 잊으면 그때 테스트가 실패한다
- **파일** `server/.../user/AccountService.java`, `src/test/.../user/AccountDeletionTest.java`

손으로 적은 목록은 잊어도 조용히 통과합니다. **잊을 수 있는 걸 잊지 못하게 만드는 쪽**이 기억하려고 애쓰는 것보다 확실했습니다.

### 화면을 채우려고 넣은 예시 데이터가 사실처럼 굳어 있었습니다

- **증상** 없음. 화면은 늘 그럴듯했다
- **원인** 홈을 열 때 오늘 기록이 없으면 예시 식단·물·운동을 만들어 넣고 있었다. 차트의 지난 6일도 고정된 예시 배열이었고, 식단 분석의 탄·단·지 비율은 기록에 없는 값이라 칼로리에서 만들어낸 숫자였다. 처음엔 화면을 확인하려고 넣은 것인데, 기능이 다 붙은 뒤에도 남아 있었다
- **왜 문제인가** 만들어 둔 빈 상태 문구는 한 번도 보인 적이 없었고, 예시 기록의 ID가 UUID가 아니라 회원이 그걸 지우면 서버 동기화가 실패했다. 무엇보다 **아무것도 기록하지 않은 사람에게 "오늘 950ml 마셨다"고 말하는 화면**이었다
- **해결** 예시 생성기와 예시 배열을 지우고, 기록에서 나오는 값만 그린다. 기록이 없는 날은 막대를 그리지 않고, 평균은 기록한 날로만 나눈다. 아직 데이터 소스가 없는 걸음 수는 `0`이 아니라 "연결 전"으로 적는다. 탄·단·지는 식품 영양 정보를 붙인 뒤에 되살린다
- **파일** `src/store/useAppStore.ts`, `src/utils/history.ts`, 홈 카드와 상세 화면 전반

건강 앱에서 숫자는 사용자가 자기 몸에 대해 내리는 판단의 근거입니다. 화면을 채우는 것보다 **비어 있다고 정확히 말하는 것**이 먼저였습니다.

### 올리지 못한 기록이 조용히 사라지고 있었습니다

- **증상** 없음. 화면에는 기록이 그대로 남아 있다
- **원인** 로컬 우선 구조라 기록은 기기에 먼저 저장되고 화면은 성공한 것으로 그려진다. 서버가 거절한 작업은 5번 재시도한 뒤 큐에서 **버렸고**, 토큰 갱신이 거절되면 **조용히 로그아웃**됐다. 둘 다 알림이 없어서, 기기에만 남은 기록이 폰을 바꿀 때 사라지는 걸 알 방법이 없었다
- **해결** 버리는 대신 실패 목록으로 옮겨 설정 화면에 무엇이 왜 실패했는지 보여주고, 다시 시도를 둔다. 로그인이 풀리면 안내창을 띄운다 — 사용자가 움직여야 복구되는 오류라 토스트로는 놓친다. 연결이 없는 경우는 그대로 대기시킨다(오프라인은 실패가 아니다)
- **파일** `src/store/useOutboxStore.ts`, `src/sync/syncEngine.ts`, `src/components/SessionExpiredModal.tsx`

낙관적 업데이트는 성공을 먼저 보여주는 대신, **실패했을 때 알려줄 책임**을 같이 진다고 봤습니다.

### 레시피 하나 때문에 게스트 기록 전체가 옮겨지지 않았습니다

- **증상** 게스트로 쓰다 가입하면 "계정은 만들었지만 기록 옮기기는 실패했어요". 레시피나 직접 입력 재료를 만든 적 없는 사람은 정상
- **원인** 앱이 보내는 모양과 서버가 받는 모양이 달랐다. 레시피 재료는 앱이 `grams`로, 서버는 `amount`(필수)로 받았고, 직접 입력 재료는 앱이 `caloriesPer100g`로, 서버는 `calories`(필수)로 받았다. 가져오기는 한 요청 안에서 전부 저장하거나 전부 거절하므로, **레시피 하나 때문에 식단·물·운동 기록까지 함께 거절**됐다
- **왜 늦게 찾았나** 서버 테스트는 서버 모양으로 요청을 만들어서 통과했다. 앱 쪽 타입은 서버 DTO를 보고 만든 게 아니라 명세 초안을 보고 만든 채로 남아 있었다. 두 쪽이 각자 맞는데 서로 안 맞는 상태
- **같이 찾은 것** 이 세 종류(레시피·루틴·직접 입력 재료)는 동기화 대기열에 아예 없었다. 서버 API는 다 있었는데, 가입할 때 한 번 올라간 뒤로 새로 만든 건 기기에만 남았다
- **해결** 앱 타입을 서버 DTO와 1:1로 맞추고, 세 종류를 대기열에 태웠다. 내려받을 때는 서버 목록과 기기 목록을 합쳐서, **기기에만 있는 항목은 지우지 않고 올린다** — 그동안 못 올라간 것들이다. 실제 서버에 붙여 게스트 가입(레시피·루틴·재료·식단·물 모두 옮겨짐) → 기기에만 있던 항목 업로드 → 화면에서 삭제 후 서버 반영까지 확인했다
- **파일** `src/api/types.ts`, `src/api/mappers.ts`, `src/sync/syncEngine.ts`, `src/sync/pull.ts`

양쪽 테스트가 모두 통과해도 **경계에서 실제로 한 번 주고받아 보기 전에는** 맞는지 알 수 없었습니다.

### 잠든 서버를 깨우는 첫 요청은 폰이 먼저 끊어버립니다

- **증상** 운영 서버에 붙은 폰에서 첫 로그인이 실패한다. 곧바로 다시 누르면 된다
- **원인** 무료 요금제 서버는 15분 쉬면 잠들고, 다시 깨는 데 실측 93.8초가 걸린다. 그런데 iOS는 요청 하나를 60초에서 스스로 끊는다. 이 제한은 앱 코드에서 바꿀 수 없다
- **처음 시도한 방법과 그게 왜 틀렸나** 실패한 요청이 서버를 깨워둔 상태이니 같은 요청을 두 번 더 보내면 된다고 생각했다. 구현한 뒤 스스로 점검하다 깨달았는데, **시간 초과는 "실패했다"가 아니라 "응답을 못 받았다"는 뜻이다.** 서버는 깨어난 다음 그 요청을 처리한다. 비밀번호 변경을 다시 보내면 이미 바뀐 비밀번호로 검사해 401이 오고(바뀌었는데 실패로 보인다), 가입은 방금 만든 계정 때문에 409가 온다
- **해결** 아무 일도 하지 않는 `GET /health`를 먼저 두드려 서버가 깨어난 것을 확인하고, 진짜 요청은 **한 번만** 보낸다. 깨우는 요청은 몇 번을 보내도 서버 상태가 달라지지 않는다
- **같이 한 것** 3초가 지나면 버튼 아래에 "서버를 깨우는 중이에요. 처음 연결은 1분 넘게 걸릴 수 있어요", 30초가 지나면 "거의 다 됐어요"로 바꾼다
- **파일** `src/api/client.ts`, `src/hooks/useWakeNotice.ts`

무료 요금제의 제약을 없앨 수는 없어서, **무슨 일이 일어나는지 알려주고 대신 기다려 주는 쪽**으로 풀었습니다. 스피너만 1분 30초를 돌면 사용자는 고장으로 판단하고 앱을 지웁니다.

재시도는 **같은 요청을 두 번 보내도 결과가 같은 API에만** 걸 수 있다는 걸 이 건에서 배웠습니다.

### 같은 회색 글씨가 카드 위치마다 다르게 보였습니다

- **증상** 보조 글씨 대비를 4.7:1로 맞춰 놨는데, 화면 위쪽 카드에서는 여전히 흐리게 보인다. 아래쪽 카드에서는 멀쩡하다
- **원인** 시간대 색을 화면 위 300px에 옅은 그라데이션으로 깔아 뒀다. 카드는 반투명이라 그 위를 지나는 카드마다 **배경색이 조금씩 다른 상태**였다. 대비는 글씨 색과 배경색 한 쌍으로 재는데, 배경이 카드 위치에 따라 달라지니 측정값 자체가 한 값이 아니었다
- **해결** 색을 **위쪽 한 덩어리에만** 깔고 끝에서 배경색으로 떨어뜨렸다. 그 아래는 고정 배경이라 어느 카드든 같은 배경 위에 있다. 색이 닿는 높이는 화면마다 다르게 준다 — 홈은 인사·브리핑까지 260, 다른 탭은 제목 줄만 130. 다크 모드에서는 같은 색을 옅게 쓴다(넓은 밝은 면이 어두운 화면에서 눈부시다)
- **파일** `src/components/ScreenBackground.tsx`

대비는 글씨 색만의 문제가 아니라 **배경이 한 값으로 고정돼 있어야** 성립한다는 걸 늦게 알았습니다.

### 본문 없는 요청을 "너무 크다"며 막고 있었습니다

- **증상** 이메일 인증 "코드 보내기"(본문 없는 POST)가 `413 PAYLOAD_TOO_LARGE`로 실패한다. 테스트에서 처음 드러났다
- **원인** 요청 크기 필터가 "크기를 안 밝힌 POST"를 전부 막고 있었다. 원래 막으려던 건 크기를 모른 채 들어오는 **청크 전송 본문**인데, 본문이 아예 없는 POST도 크기를 안 밝히기는 마찬가지라 같이 걸렸다. 지금까지 모든 POST에 본문이 있어서 아무도 몰랐다
- **해결** HTTP에서 본문은 `Content-Length`나 `Transfer-Encoding` 중 하나가 있을 때만 존재한다. 크기가 없고 청크 전송일 때만 막도록 좁혔다. 막던 공격은 그대로 막힌다
- **파일** `server/.../common/PayloadSizeFilter.java`

그대로 배포했다면 이메일 인증 버튼은 항상 "보낸 데이터가 너무 커요"로 실패했을 겁니다. 보안 필터는 **막는 것만큼 통과시키는 것도** 테스트해야 한다는 걸 배웠습니다.

### 입력칸 여백이 웹에서만 안 먹고 있었습니다

- **증상** 재료 검색 칸에 돋보기를 넣었더니 입력한 글씨가 돋보기 밑으로 들어간다. 확인해 보니 원래 있던 지우기(×) 버튼 자리도 비워지지 않은 채였다
- **원인** 입력칸 기본 스타일은 좌우 여백을 `paddingHorizontal: 14`로 묶어 두고, ×나 돋보기가 있을 때만 `paddingLeft·paddingRight: 44`를 뒤에 덧붙였다. 네이티브에서는 뒤에 준 값이 이기지만, 웹은 스타일을 CSS 클래스로 바꾸면서 **묶음 값(padding-inline)과 한쪽 값(padding-left)이 다른 속성**이 되고, 둘 중 무엇이 이길지는 배열 순서가 아니라 CSS가 만들어진 순서가 정한다
- **해결** 기본 여백부터 `paddingLeft`·`paddingRight`로 따로 적었다. 같은 속성끼리 덮어쓰게 되니 순서대로 이긴다
- **파일** `src/components/TextField.tsx`

긴 이름을 넣어야만 보이는 문제라 한동안 몰랐습니다. 브라우저에서 계산된 여백 값을 직접 찍어 보고서야 원인이 스타일 순서가 아니라 속성 이름이라는 걸 알았습니다.

### 지운 체중 기록을 되살리면 현재 체중이 옛날 값으로 돌아갔습니다

- **증상** 체중 기록 목록에서 옛 날짜 하나를 지우고 "실행 취소"를 누르면 기록은 돌아오는데, 프로필의 현재 체중이 그 옛날 값으로 바뀐다. 목표 칼로리도 따라 바뀐다
- **원인** 체중을 기록하는 액션이 날짜와 상관없이 **항상 프로필 체중을 그 값으로 덮어썼다.** 지금까지는 오늘 기록만 넣을 수 있어서 드러나지 않았는데, 실행 취소가 처음으로 과거 날짜를 넣는 경로가 됐다
- **해결** 넣은 날짜가 가장 최근일 때만 프로필 체중이 따라가게 했다. 화면 쪽이 아니라 액션 한 곳에서 고쳐서, 나중에 날짜를 골라 기록하는 화면이 생겨도 같은 규칙을 탄다
- **파일** `src/store/useAppStore.ts`

### 미리보기를 누르면 실제 기록이 바뀌고 있었습니다

- **증상** 알림 설정의 "피또 표정 5단계"에서 표정을 누르면 오늘 물 섭취량이 그 단계에 맞게 바뀐다
- **원인** 표정을 보여 주려고 오늘 물 기록을 그 단계의 값으로 **실제로 고치는** 방식으로 만들어 두었다. 게스트일 때도 기록이 바뀌고, 회원이면 서버까지 올라간다
- **해결** 표정과 한마디만 미리 보고 기록은 건드리지 않게 했다

화면 개편 중에 버튼 모양을 고치다가 동작을 다시 보게 되면서 찾았습니다. 미리보기는 **되돌릴 필요가 없어야** 미리보기라는 걸 적어 둡니다.

같은 테스트 실행에서 **탈퇴 테스트의 안전장치**도 새 표(`email_codes`)를 잡아냈습니다. 탈퇴 코드에는 새 표를 넣었지만, 테스트 준비 단계에서 그 표에 기록을 만들지 않아 "이 표는 검증에서 빠진다"며 멈췄습니다. 표 목록을 사람이 적지 않고 DB에 직접 묻게 해 둔 장치가 한 번 제 몫을 한 셈입니다.

## 9. 프론트 우선 구현과 데이터 경계 설계

화면과 인터랙션을 먼저 완성하는 순서로 진행했습니다. 그래서 데이터는 아직 일부가 목데이터지만, **연동 지점을 처음부터 한 곳씩 격리하고 각각이 어떤 소스로 교체될지 코드에 명시**했습니다.

| 위치 | 현재 | 교체 대상 |
|---|---|---|
| `screens/home/mockData.ts` | 지난 6일 걸음 수 | 건강 API |
| `HealthScreen`의 `sittingHours` | 고정값 6.5h | 기기 센서 |
| `data/foods.ts` | 로컬 음식 목록 | 식품영양성분 API |
| `utils/periodMock.ts` | 생성된 주기 데이터 | 사용자 입력 기록 |

각 지점에 "실제 데이터 소스 연동 전까지", "기기 센서 연동 전 예시값" 형태의 주석을 달아 연동 시 무엇을 건드려야 하는지가 코드에서 바로 보이게 했습니다. UI 컴포넌트는 데이터의 출처를 모르고 형태만 알기 때문에, 소스가 바뀌어도 화면 코드는 그대로입니다.

**화면을 먼저 만든 이유**

기록 앱에서 가장 불확실한 부분은 데이터 구조가 아니라 "이 화면을 매일 열게 되는가"였습니다. 그 답은 화면을 만들어 써봐야 나옵니다. 다만 이 순서에는 함정이 있습니다. 목데이터로 화면을 완성하면 화면이 목데이터의 형태에 맞춰 굳고, 나중에 실제 소스를 붙일 때 화면까지 다시 고치게 됩니다. 경계를 먼저 그어둔 이유가 그것입니다.

## 10. 앱과 서버 사이의 계약

서버 코드를 짜기 전에 **API 명세서를 먼저 작성**했고, 한 번 개정해 v1.1까지 갔습니다. v1.0에서 고친 것들:

| 항목 | v1.0 | v1.1 | 이유 |
|---|---|---|---|
| 식사 메모 | 음식 단위 | 날짜 + 끼니 단위 | 원래 구조로는 "오늘 아침 메모"를 저장할 곳이 없었음 |
| 수분 기록 | 누적 POST | 절댓값 PUT | 네트워크 재시도로 같은 값이 두 번 더해짐 |
| 음식 양 | `"1공기 210g × 2"` 문자열 | 숫자 + 단위 | 문자열은 계산도 검증도 불가 |
| 활동량 | 숫자 계수 `1.375` | 코드 `light` | 계수를 조정하면 저장된 데이터가 전부 어긋남 |

이 결함들을 **구현 전에 발견한 것**이 가장 큰 소득이었습니다. 다 만든 뒤에 알았다면 앱·서버·DB를 동시에 고쳐야 했습니다.

**게스트 모드 — 회원가입을 강제하지 않는다**

가입 없이 모든 기능을 쓰고 기록은 기기에 저장합니다. 가입하면 기기 기록을 한 번에 서버로 올립니다(`POST /me/import`).

기록 앱은 첫날 한 줄을 남기게 만드는 것이 전부입니다. 시작하자마자 회원가입 화면이 뜨면 그 전에 이탈합니다. 설계상의 이득도 있었습니다. 가입이 "기능을 여는 열쇠"가 아니라 "저장 위치를 옮기는 스위치"가 되면서 **로그인 가드가 통째로 사라졌습니다.** 앱의 가드는 온보딩 완료 여부 하나뿐입니다.

**클라이언트가 ID를 만든다**

기록의 ID(UUID)를 앱이 만들어 보내고, 서버는 처음 보는 ID면 생성하고 이미 있으면 기존 것을 돌려줍니다. 앱은 버튼을 누르는 즉시 화면에 반영하고 오프라인에서도 기록을 만듭니다. 클라이언트 ID를 쓰면 동기화할 때 임시 ID를 바꿔치기할 필요가 없고, 재시도로 같은 기록이 두 번 생기지 않습니다.

**계산은 서버가 기준**

목표 칼로리·물 목표·운동 소모 칼로리는 서버 값이 최종값입니다. 앱에도 같은 공식이 있지만 게스트 모드용이자 저장 전 미리보기용입니다. 공식이 두 곳에 있으면 언젠가 어긋나므로, 명세의 예시 값(여성 26세 165cm 55kg → 1424kcal / 1800ml)을 **양쪽 테스트에 같이 박아두었습니다.** 한쪽을 고치면 다른 쪽 테스트가 깨집니다.

## 11. 서버 구현에서의 판단

**인증** — access 30분 + refresh 14일. refresh는 갱신할 때마다 새로 발급하고(로테이션), 이미 쓴 토큰이 다시 오면 탈취로 보고 그 사용자의 토큰을 전부 폐기합니다. 토큰은 원본이 아니라 해시로 저장해 DB가 유출돼도 그 값으로 갱신할 수 없게 했습니다.

**로그인 응답을 갈라놓지 않음** — 계정이 없을 때와 비밀번호가 틀렸을 때 같은 메시지를 줍니다. 응답이 다르면 특정 이메일의 가입 여부를 확인하는 통로가 됩니다.

**에러 응답 한 모양** — 모든 실패가 `{ status, code, message }`로 나갑니다. `code`로 앱이 분기하고, `message`는 그대로 화면에 띄울 수 있는 문장입니다. 앱이 에러 코드마다 문구를 따로 관리하지 않아도 됩니다.

**패키지는 도메인별로** — 계층별(controller/service/repository)로 나누면 기능 하나를 고칠 때 폴더 세 개를 오갑니다. 도메인별로 두면 한 폴더 안에서 끝납니다.

**멱등 처리 — 같은 ID로 다시 오면 201이 아니라 200** — 기록의 ID를 앱이 만들어 보내므로, 이미 있는 ID면 새로 만들지 않고 기존 기록을 돌려줍니다. 오프라인에서 만든 기록을 재시도해도 중복이 생기지 않습니다. 다른 사용자가 쓰는 ID면 `409`입니다.

**조회 단계에서 소유자를 함께 본다** — `findByIdAndUserId(id, userId)` 형태로만 조회합니다. `findById`로 가져와 나중에 소유자를 비교하는 방식은 비교를 한 번 빼먹으면 그대로 구멍이 됩니다. 조회 자체에 넣으면 빼먹을 수가 없습니다.

**계산할 근거가 없으면 거절한다** — 목록에 없는 운동인데 앱이 칼로리도 안 보냈으면 `400`을 줍니다. 0으로 저장하면 사용자가 "0kcal 소모"를 사실로 믿게 됩니다. 앱에서 "추정값을 사실처럼 보여주지 않는다"고 정한 것과 같은 원칙입니다.

**로그는 양쪽 방향을 따로 본다** — 사용자에게는 덜 주고 서버에는 더 남깁니다. 응답의 `500` 메시지는 어떤 경우에도 고정 문구라 스택 트레이스·SQL·접속 정보가 나가지 않습니다. 대신 서버에는 보안 이벤트를 남깁니다 — 로그인 실패·차단, 인증·권한 실패, 횟수 제한, 그리고 **토큰 재사용 감지**입니다. 마지막 것은 사용자가 갑자기 전부 로그아웃되는 상황이라, 기록이 없으면 나중에 원인을 찾을 수 없습니다.

남길 때도 가립니다. 이메일은 앞 두 글자만 남기고(`vi***@fitto.app`), 사용자 식별이 필요한 곳은 `userId`를 씁니다. **로그가 유출되면 그게 가입자 명단**이기 때문입니다. 로그인 실패 사유(계정 없음 / 비밀번호 틀림)도 적지 않습니다 — 응답에서 막아둔 것을 로그로 흘리면 의미가 없습니다. 예외 메시지 대신 예외 종류만 남기는 것도 같은 이유로, 파싱 실패 메시지에는 요청 본문 조각이 섞여 들어올 수 있고 로그인 요청이라면 그게 비밀번호입니다.

**게스트 데이터 이전은 서버 값이 이긴다** — 가입할 때 기기 기록을 올리면, ID가 겹치는 기록은 건너뛰고 날짜가 겹치는 기록은 서버 값을 유지합니다. 다른 기기에서 쓰던 기록을 오래 방치된 기기의 값으로 덮어쓰는 쪽이 더 큰 사고이기 때문입니다. 전체가 한 트랜잭션이라 중간에 실패하면 아무것도 저장되지 않습니다.

## 12. 앱과 서버를 잇는 방식 — 로컬 우선과 대기열

처음 계획은 서버 상태 캐싱 라이브러리(TanStack Query)를 넣는 것이었습니다. 코드를 보고 방향을 바꿨습니다.

그걸 도입하면 **화면 20개가 전부 서버 캐시를 읽도록 다시 쓰여야** 했습니다. 지금 모든 화면이 기기 저장소(zustand)를 보고 그리고 있으니까요. 그런데 실제로 풀어야 할 문제는 "화면이 어디서 데이터를 읽는가"가 아니라 **"기록이 서버까지 도달하는가"** 였습니다.

그래서 화면은 그대로 두고 뒤에 대기열을 놓았습니다.

```
버튼 누름 → 기기 저장소 반영(화면은 여기만 본다) → 대기열에 적재 → 순서대로 전송
```

**이 구조가 자동으로 해결한 것들**

| 보통 따로 구현하는 것 | 이 구조에서 |
|---|---|
| 낙관적 업데이트 | 화면이 이미 로컬을 보므로 공짜. 되돌리기 로직도 불필요 |
| 오프라인 지원 | 기본 동작. 대기열을 기기에 저장해 앱을 껐다 켜도 남음 |
| 화면 수정 | 한 줄도 안 고침. 스토어 액션 안에서만 대기열에 넣음 |

**대기열에 값을 넣지 않았습니다**

"무엇이 바뀌었는지"만 적고, 보낼 때 저장소에서 최신 값을 읽습니다. 물을 다섯 번 누르면 대기열에는 한 건만 남고 마지막 값 한 번만 올라갑니다. 값을 그대로 담았다면 다섯 번 보냈을 겁니다.

**순서대로 하나씩 보냅니다**

병렬이 빠르지만 "추가 → 삭제"가 뒤집혀 도착하면 지운 기록이 되살아납니다. 기록 앱에서 그 위험이 속도보다 크다고 봤습니다.

**실패를 세 가지로 나눴습니다**

연결이 없을 때는 실패로 세지 않고 대기열을 유지합니다. 비행기 모드가 길어졌다고 기록을 버리면 안 되니까요. `401`은 토큰을 갱신해 같은 작업을 다시 보냅니다. 서버가 거절한 요청은 횟수를 세고 5회를 넘기면 대기열에서 빼 **실패 목록**으로 옮깁니다. 처음엔 버렸는데, 기기에만 남은 기록은 폰을 바꾸면 사라져서 설정에 사유와 함께 보여주고 다시 시도할 수 있게 바꿨습니다(8장). 대기열에서 빼는 이유는 — **고칠 수 없는 요청 하나가 뒤의 기록을 영영 막지 않게** 하려는 규칙입니다. 실제로 운동 기록이 500으로 실패하는 동안에도 물 기록은 정상적으로 올라갔습니다.

**내려받기는 올리기 뒤에만**

순서를 바꾸면 아직 못 올린 기록이 서버 값으로 덮여 사라집니다. 내려받기 함수 안에서도 대기열이 비어 있는지 한 번 더 확인합니다. 그리고 **서버가 준 날짜만** 덮어씁니다 — 서버에 없는 날짜의 기기 기록은 아직 못 올린 것일 수 있어서 건드리지 않습니다.

**지난 날짜는 열 때 받아옵니다**

로그인할 때 받아오는 범위는 걸음·체중처럼 기간으로 한 번에 받을 수 있는 것만 30일이고, 식단·운동·물은 **이틀치**뿐입니다. 이 세 가지는 서버 API가 날짜별 조회라 30일치를 받으려면 요청이 90번 나갑니다. 무료 요금제 서버에 로그인할 때마다 그렇게 부을 수는 없었습니다.

대신 달력을 넘겨 지난 날짜를 열면 그때 그 날짜만 받아옵니다(`src/sync/pullDate.ts`). 한 번 받은 날짜는 기억해 두고 다시 받지 않고, 같은 날짜를 여러 화면이 동시에 부르면 요청 하나로 묶습니다. 밀어올리기가 끝나야 받는 규칙은 여기서도 같습니다 — 아직 못 올린 기록이 있는데 서버 값으로 덮으면 그게 사라집니다.

**"기록이 없다"고 단정하기 전에 확인합니다.** 받아오는 동안에는 빈 상태 문구 대신 "불러오는 중이에요"를 보여줍니다. 없는 것과 아직 모르는 것은 다른데, 둘을 같은 화면으로 보여주면 사용자는 기록이 지워졌다고 생각합니다.

계정이 바뀌면 "이미 받았다"는 기억을 버립니다. 로그아웃·세션 만료·다른 계정 로그인 경로가 각각 있어서, 화면마다 지우는 대신 인증 상태를 한 곳에서 지켜보게 했습니다. 안 지우면 다음 계정에서 그 날짜를 받아오지 않아 **서버에 기록이 있는데도 빈 화면**이 됩니다.

**무한 반복을 막은 지점**

처음에는 서버에서 받은 프로필을 `setProfile`로 넣었는데, 그 액션이 대기열에 쌓는 구조라 **받은 값을 다시 올려보내고 또 받는** 순환이 생겼습니다. 서버 값 반영 전용 액션을 따로 만들어 이 경로는 대기열을 건드리지 않게 했습니다.

## 12-1. 화면 잠금 — 비밀번호를 하나 더 만들지 않았습니다

건강·생리 기록은 폰을 잠깐 빌려준 사이에도 보이면 안 되는 정보라 화면 잠금을 넣었습니다. 처음엔 앱 전용 간편비밀번호도 고려했는데 뺐습니다. 폰에는 이미 지문·얼굴·PIN이 있고, 앱이 비밀번호를 하나 더 받으면 **사용자는 외울 게 늘고 앱은 그걸 안전하게 보관할 책임이 생깁니다.** `expo-local-authentication`으로 폰 잠금을 그대로 빌려 쓰고, 지문·얼굴이 안 되면 OS가 폰 PIN 입력으로 넘겨줍니다.

**잠그는 것만으로는 부족했습니다.** 최근 앱 목록의 미리보기는 앱이 뒤로 가는 순간 찍힙니다. 잠금을 걸어 놔도 그 순간 화면이 그대로면 생리 기록이나 체중이 미리보기로 보입니다. 그래서 앱이 `active`가 아니게 되는 즉시 화면을 덮습니다.

다시 잠그는 기준은 **30초**입니다. 0초면 음식 사진을 찍으러 카메라에 다녀올 때마다 지문을 대야 하고, 너무 길면 잠금의 의미가 없습니다.

구현하면서 막은 함정이 세 가지 있었습니다.

- **저장된 설정은 비동기로 올라옵니다.** 앱이 켜지는 순간엔 "잠금 꺼짐"(기본값)으로 보여서 그대로 판단하면 잠금을 건너뜁니다. 저장소가 다 올라온 뒤(`onFinishHydration`)에 잠글지 정합니다
- **인증 창 자체가 앱을 뒤로 보냅니다.** 안드로이드에서 PIN 입력 화면이 뜨면 앱이 백그라운드로 잡히는데, 이걸 "나갔다 옴"으로 세면 PIN을 30초 넘게 치는 동안 또 잠겨서 끝나지 않습니다. 인증 중에는 상태 변화를 무시합니다
- **폰 잠금을 없애면 확인할 방법이 없습니다.** 여기서 막으면 앱을 영영 못 엽니다. 이 경우엔 화면 잠금을 스스로 끄고 그렇다고 알려줍니다

켤 때와 끌 때 모두 본인 확인을 받습니다. 켤 때는 폰에 잠금이 정말 있는지 보려는 것이고, 끌 때는 폰을 잠깐 빌린 사람이 잠금을 꺼두고 돌려주는 걸 막으려는 것입니다.

## 12-2. 비밀번호 찾기·이메일 인증 — 가입 여부를 다시 새지 않게

보안 점검 때 로그인·가입에서 **가입 여부가 새는 길**을 막았습니다(응답 문구, 응답 시간). 비밀번호 찾기는 그 길을 다시 여는 가장 쉬운 기능입니다 — "가입되지 않은 이메일이에요"라고 답하는 순간 누구나 남의 가입 여부를 확인할 수 있습니다.

그래서 코드 요청은 **가입 여부와 상관없이 항상 202**입니다. 문구만 같게 하면 부족해서, 계정 찾기·코드 해싱·메일 발송을 전부 **응답을 보낸 뒤에** 합니다. 가입된 이메일일 때만 이 일들이 응답 전에 일어나면 수백 ms 차이가 나고, 그걸 재면 가입 여부가 드러납니다. 로그인에서 더미 해시로 시간을 맞춘 것과 같은 문제를 다른 방법으로 풀었습니다. 재설정도 없는 계정·틀린 코드·만료된 코드를 한 가지 오류로 답합니다.

**링크 대신 6자리 코드**를 고른 이유는 앱이라서입니다. 링크는 누르면 앱으로 돌아오게 하는 딥링크와 받아줄 웹 페이지가 따로 필요합니다. 코드는 메일에서 보고 옮겨 치면 끝입니다.

코드는 **BCrypt로** 저장합니다. refreshToken은 SHA-256으로 충분했는데(원래 무작위라 되돌릴 수 없다), 6자리는 경우의 수가 백만 개뿐이라 DB가 새는 순간 전부 되돌릴 수 있습니다. 10분 유효, 한 번 쓰면 삭제, 코드 하나당 5번까지 틀릴 수 있습니다. 틀린 횟수는 오류로 거절하면서도 **저장돼야** 해서 트랜잭션이 이 예외에는 롤백하지 않게 했습니다 — 롤백되면 몇 번을 틀려도 0번으로 남습니다.

**이메일 인증은 가입 뒤에** 받습니다. 가입 전에 요구하면 "인증 대기 중인 가입"을 따로 보관해야 하고 게스트 기록 옮기기까지 흐름이 길어집니다. 인증을 받는 이유는 하나, 오타 난 주소로 가입하면 비밀번호를 찾을 방법이 없어서입니다. 비밀번호 찾기로 코드를 맞혀도 메일함을 연 것이니 인증된 것으로 봅니다.

**메일 서비스는 아직 붙이지 않았습니다.** 무료 서버는 SMTP 포트가 막혀 HTTP 메일 API가 필요하고, 그러려면 보내는 도메인이 있어야 합니다. 그 전까지 로컬에서만 코드를 서버 로그에 찍고, 운영에서 이 설정이 켜지면 **부팅을 실패시킵니다** — 로그를 볼 수 있는 누구나 남의 비밀번호를 바꿀 수 있게 되기 때문입니다.

앱은 재설정 뒤 바로 로그인시키지 않고 로그인 화면으로 보냅니다. 서버는 토큰을 같이 주지만, 이 기기에 게스트 기록이 있으면 "계정에 합칠지"를 물어야 하고 그 질문이 로그인 화면에 있습니다.

## 12-3. 약관 동의 — 앱 체크만이 아니라 서버에 증거를 남긴다

가입 직전에 시트를 하나 띄워 이용약관·개인정보·건강 정보 세 가지 동의를 받습니다. 셋 다 필수이고, 체크해야 "동의하고 계정 만들기"가 켜집니다.

**건강 정보를 개인정보와 따로 받습니다.** 몸무게·질환·알레르기·생리 주기는 법에서 민감정보로 따로 동의를 받게 되어 있습니다. 개인정보 동의 한 줄에 묶으면 나중에 "건강 정보까지 동의한 적은 없다"는 말에 답할 수 없습니다.

**동의 기록은 서버에 남깁니다.** 앱에서 체크박스만 확인하고 끝낼 수도 있었습니다. 그러면 앱 버튼이 막아줄 뿐이고, 요청을 직접 보내는 사람이나 앱의 버그는 막지 못합니다. 그래서 가입 요청에 `agreements`를 필수로 넣고, 서버가 셋 다 `true`인지 한 번 더 검사합니다(`@AssertTrue`). 통과하면 동의 시각 셋과 약관 버전을 `users`에 저장합니다.

- **시각은 서버 시계로 찍습니다.** 앱이 보낸 시각은 기기 시계를 바꾸면 얼마든지 달라집니다. 증거로 쓰려면 받는 쪽이 찍어야 합니다.
- **버전은 약관 시행일입니다.** 약관을 고치면 누가 옛 약관에 동의했는지 알아야 다시 동의를 받을 수 있습니다. 앱은 `src/data/terms.ts`의 `TERMS_VERSION`을 보냅니다.
- **동의 기록은 응답에 담지 않습니다.** 앱이 쓸 데가 없는 값을 내보내지 않습니다.

이 칸이 생기기 전에 가입한 계정은 비어 있습니다. 지금은 계정이 개발용뿐이라 출시 전에 한 번 동의를 받으면 됩니다.

"보기"를 누르면 시트를 잠깐 닫고 본문 화면으로 갑니다. 시트는 화면 위에 뜨는 창이라 그대로 두면 본문을 가립니다. 돌아오면 시트가 다시 열리고, 체크 상태는 가입 화면이 들고 있어서 그대로 남습니다. 설정의 "약관 및 정책"에서도 같은 본문 화면을 봅니다.

**"보기"는 시트 안에서 넘깁니다.** 처음엔 본문 화면으로 이동했는데, 가입 화면이 설정 탭 안에 있어서 아래 탭바에 "설정"이 켜진 채 보였습니다. 약관을 보려다 설정으로 넘어간 것처럼 느껴집니다. 시트 위에 창을 하나 더 띄우는 방법은 창 두 개의 닫힘 순서와 뒤로가기가 꼬이기 쉬워서, 같은 시트의 내용을 본문으로 바꾸고 제목 옆 ‹로 돌아오게 했습니다.

## 12-4. 탈퇴 — 이유는 남기되 누구인지는 남기지 않는다

탈퇴는 세 단계입니다. 무엇이 지워지는지 보고 이유를 고르고(선택) → 비밀번호로 본인 확인 → 알림창에서 마지막 확인.

**사유는 익명으로 서버에 남깁니다.** 출시하면 "왜 떠나는지"가 앱을 고치는 가장 직접적인 근거입니다. 다만 탈퇴하면 개인정보는 지워야 하므로, `deletion_reasons` 표에 사유 코드와 시각만 두고 `user_id`나 이메일은 넣지 않았습니다. 사람을 가리키는 값이 없으면 남겨도 개인정보가 아닙니다. 탈퇴 테스트는 "`user_id` 칸이 있는 표는 전부 비었나"를 DB에 직접 묻는데, 이 표에 그 칸이 생기면 테스트가 바로 잡습니다.

**직접 쓰는 칸은 두지 않았습니다.** 사람들은 자유 입력 칸에 연락처나 병명을 적습니다. 그 순간 익명이 깨지고 보관 책임이 생깁니다. 고르는 사유 여섯 개면 월별 비율을 보기에 충분합니다.

**알림 때문에 떠나려는 사람에겐 다른 길을 보여줍니다.** 사유 카드 아래 "알림만 줄일 수 있어요 · 알림 설정"을 두었습니다. 탈퇴는 되돌릴 수 없지만 알림 설정은 언제든 바꿀 수 있습니다.

**마지막 확인창에서 칠한 버튼은 "취소"입니다.** 알림창은 원래 "칠한 버튼 하나 + 회색 나중에"인데, 여기서 칠한 쪽을 "탈퇴하기"로 두면 되돌릴 수 없는 동작을 권하는 셈입니다. 위험한 쪽은 테두리 버튼에 빨간 글씨로 한 발 물렸습니다. 요청이 나간 뒤에는 "취소"를 막습니다. 창만 닫히고 계정은 지워지면 사용자는 취소한 줄 압니다.

**표를 추가할 땐 엔티티와 SQL이 둘 다 필요합니다.** 처음에 마이그레이션 SQL만 쓰고 엔티티를 만들지 않아 테스트가 깨졌습니다. 테스트와 로컬은 엔티티를 보고 표를 만들고(`ddl-auto`), 운영은 SQL로만 만든 뒤 엔티티와 맞는지 검사합니다(`validate`). 한쪽만 있으면 둘 중 한 환경에서 표가 없습니다.

## 12-5. 로딩 — 기기 기본 스피너를 쓰지 않았습니다

기본 스피너는 아이폰과 안드로이드에서 모양이 다르고, 버튼 글씨색을 그대로 받아 탈퇴 버튼에서는 빨간 원이 돌았습니다. 피또가 물방울이라 버튼 안에서는 물방울 셋이 차례로 튀고, 화면 안에서 기록을 받아오는 동안에는 피또가 둥둥 떠 있고 그 아래 "기록을 불러오는 중이에요"를 적었습니다. 로딩은 사용자 환경에 따라 길이가 크게 달라서, 무엇을 기다리는지 한 줄로 알려주는 게 중요합니다.

기기에서 "동작 줄이기"를 켠 사람에게는 움직이지 않습니다. 움직임은 스크린리더에 보이지 않으므로 "불러오는 중"을 따로 읽어줍니다.

**토스트는 세 번 바꿨습니다.** 시안의 어두운 반투명은 탭바와 겹쳐 뒤가 비쳤고, 불투명 남색으로 바꾸니 밝은 홈에서 너무 무거웠습니다. 결국 탭바와 같은 밝은 유리(흰 면 95% + 흐림 + 그림자)에 진한 글씨로 정했습니다. 유리 면은 뒤에 무엇이 있느냐에 따라 대비가 흔들려서, 면을 충분히 채워(95%) 어떤 배경 위에서도 글씨가 읽히게 했습니다. 자리도 떠 있는 탭바 바로 위로 옮겼습니다. 물 카드도 힘을 뺐습니다 — 홈에서 하나뿐이던 칠한 버튼(+250 ml)을 파란 글씨로, 그라데이션 물과 물결은 옅은 단색으로 바꿨습니다. 가장 자주 누르는 버튼이라고 가장 크게 칠할 필요는 없습니다.

## 12-6. 데이터 초기화 — 명세에만 있던 API

회원이 설정에서 데이터 초기화를 하면 기기 기록만 지워지고 있었습니다. 서버의 `DELETE /users/me/records`를 앱이 안 부른다고 생각했는데, 찾아보니 **서버에도 구현이 없었습니다.** 명세를 먼저 쓰고 구현하면서 이 줄만 빠졌고, 앱도 부르지 않으니 아무 오류 없이 지나갔습니다. 다음 동기화 때 지운 기록이 다시 내려올 수 있는 상태였습니다.

- **지우는 목록은 탈퇴와 같은 코드를 씁니다.** 탈퇴는 "기록 표 + 계정 표", 초기화는 "기록 표"만. 목록을 따로 두면 표를 추가할 때 한쪽만 고치게 됩니다.
- **프로필은 서버에서 비우지 않습니다.** 앱이 온보딩을 다시 받고 마치는 순간 프로필을 덮어씁니다. 서버에서 먼저 비우면 온보딩 도중 앱이 꺼졌을 때 목표 칼로리 없는 계정이 남습니다.
- **순서는 탈퇴와 같습니다 — 서버 먼저, 성공하면 기기.** 반대면 서버 요청이 실패했을 때 기기 기록만 사라집니다.
- 테스트는 탈퇴 테스트처럼 DB에 `user_id` 칸이 있는 표를 직접 물어서, 기록 표는 비고 계정 표는 남았는지 봅니다.

고치다 하나 더 찾았습니다. **온보딩을 다시 마쳐도 프로필이 서버로 올라가지 않았습니다.** 프로필 화면에서 고칠 때만 올리고, 온보딩 완료 액션은 기기에만 저장했습니다. "온보딩 다시 보기"를 한 회원은 기기와 서버 프로필이 어긋난 채였습니다.

## 12-7. 알림 — 서버 푸시 대신 기기 예약

알림 설정 화면은 있었지만 실제로 알림을 보내는 코드는 없었습니다. 서버 푸시가 아니라 **폰이 정해진 시각에 스스로 울리게 예약하는 로컬 알림**으로 만들었습니다. 무료 서버가 잠들어 있어도 울리고, 무엇을 언제 마셨는지가 서버로 나가지 않습니다. 로컬 우선인 앱 구조와도 맞습니다.

**문구가 예약할 때 정해지는 문제.** 로컬 알림은 울리는 순간이 아니라 예약하는 순간에 문구가 고정됩니다. "목표까지 500ml"가 아침 값으로 남으면 거짓말이 됩니다. 그래서 물·식사를 기록하거나 앱을 열 때마다 **예약을 전부 다시 겁니다.** 목표를 채운 날은 남은 물 알림을 빼고, 이미 기록한 끼니의 알림도 뺍니다. 물·식사는 사흘치, 주 1회 알림과 생리는 일주일 앞까지만 걸어 iOS 예약 한도(64개) 안에 둡니다(다 켜도 50개).

**계획과 예약을 나눴습니다.** "언제, 무슨 문구로"를 정하는 부분(`notifications/plan.ts`)은 기기와 떨어진 순수 함수라 `npm run check:notify`로 방해 금지 시간, 자정을 넘는 구간, 이미 지난 시각, 목표를 채운 날을 확인합니다. 알림은 폰에서 그 시각이 돼야 울려서 눈으로 확인하기 어렵기 때문입니다.

**권한은 켤 때 묻습니다.** 앱을 켜자마자 "알림 허용?"을 띄우면 이유를 모른 채 대부분 거절합니다. 그래서 기본값을 전부 끔으로 바꾸고, 설정에서 처음 켜는 순간 묻습니다. 거절하면 OS가 다시 묻지 않으므로 "권한이 꺼져 있어요 · 설정 열기"를 보여줍니다.

**생리 알림은 잠금화면 노출을 고르게 했습니다.** 무조건 가리면("피또가 알려줄 게 있어요") 매번 앱을 열어야 해서 오히려 안 보게 되고, 무조건 보이면 옆 사람이 볼 수 있습니다. 사람마다 괜찮은 정도가 달라서 "잠금화면에 내용 보이기"를 따로 두고 기본은 가리기로 했습니다.

**Expo Go에서는 확인할 수 없었습니다.** 안드로이드 Expo Go는 SDK 53부터 원격 푸시를 빼면서, 알림 모듈을 **불러오기만 해도** 앱이 멈춥니다(로컬 알림만 써도). 그래서 그 환경에서는 모듈을 아예 불러오지 않고 설정 화면에 "개발용 빌드에서 울려요"를 띄웁니다. 실제 확인은 EAS로 만든 개발용 빌드에서 했고, 정각을 기다리지 않도록 개발 빌드에서만 보이는 "10초 뒤 테스트 알림"을 두었습니다.

**움직임 알림은 숨겼습니다.** "1시간 앉아 있으면"을 알려면 움직임 센서가 필요한데 걸음 센서가 아직 연결 전입니다. 정해진 시각에 울리는 걸로 흉내 내면 실제로 걷고 있을 때도 "일어나세요"가 옵니다.
