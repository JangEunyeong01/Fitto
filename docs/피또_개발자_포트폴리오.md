# 피또 (Fitto) — 설계 노트

> 개인 프로젝트 · 1인 개발 · React Native (Expo) + Spring Boot

화면 하나를 만들 때마다 내린 판단과 그 이유를 기록한 문서입니다. 구현 결과보다 **왜 그렇게 했는지**에 초점을 둡니다.

---

## 1. 프로젝트 개요

**피또**는 칼로리·수분·운동·생리 주기를 한 곳에서 기록하는 건강 관리 앱입니다. 숫자를 나열하는 대신 물방울 캐릭터의 표정과 움직임으로 오늘 상태를 먼저 보여주는 것을 컨셉으로 잡았습니다.

| 축 | 이 문서에서 다루는 근거 |
|---|---|
| 디자인 → 개발 연결 | 디자인 핸드오프 문서의 값을 코드 토큰으로 옮기고, 출처를 코드에 남긴 구조 |
| 인터랙션 구현 | 제스처 기반 입력, 상태에 반응하는 캐릭터 애니메이션 |
| 구조 설계 | 상태 스키마 버전 마이그레이션, 목데이터와 실데이터의 경계 분리 |
| 앱·서버 설계 | API 명세를 먼저 쓰고 그 계약에 맞춰 양쪽을 구현 |
| 스코프 판단 | 플랫폼 제약을 우회하되 기술 부채와 교체 시점을 명시한 결정들 |

---

## 2. 기술 스택

**앱** — Expo 57 / React Native 0.86 / TypeScript(strict) / Zustand(persist) / React Navigation 7 / Reanimated 4 + Gesture Handler / react-native-svg

**서버** — Java 21 / Spring Boot 4 / Spring Data JPA / PostgreSQL / JWT

**웹에서 앱으로 전환한 이유**

초기에는 웹으로 시작했지만 사용 맥락이 맞지 않았습니다. 건강 기록은 하루에 여러 번, 짧게, 손에 들고 하는 일입니다. 브라우저를 열고 주소를 치는 단계가 매번 끼어들면 기록이 이어지지 않습니다.

전환하면서 디자인 핸드오프 문서는 그대로 살아남았고(3장), 화면 구성과 계산 규칙도 재사용했습니다. 실제로 버린 것은 웹 전용 레이아웃 코드였습니다.

Expo를 고른 이유는 확인 속도입니다. 네이티브 빌드 환경 없이 폰과 웹에서 동시에 확인됩니다. 대신 네이티브 모듈 제약을 받으므로, 걸음수 센서 연동처럼 제약에 걸리는 기능은 그 지점을 코드에 명시해두었습니다(9장).

## 3. 디자인 → 코드: 핸드오프 값을 옮기는 규칙

디자인 산출물의 값을 코드로 옮기면서 **옮겼다는 사실과 출처를 코드에 남기는 규칙**을 세웠습니다.

- `src/theme/tokens.ts` 첫 줄 — "design-source README 값 그대로 이식"
- `src/utils/goals.ts` 첫 줄 — "README '온보딩 — 목표 계산식'을 그대로 옮긴 것. 수치를 임의로 바꾸지 않는다"
- 개별 토큰에도 출처 주석 — `periodBadgeGradient`에 "README: lavender .9 → peach .75"
- README에 값이 없어 **직접 판단한 부분은 그렇다고 명시** — `overlay.sheetBackdrop`에 "README에 값이 없어 튜토리얼 딤과 같은 색을 옅게 썼다"

**왜 이렇게 했는가**

디자인과 구현이 달라 보일 때, 그것이 *구현 실수*인지 *의도적 판단*인지 코드만 봐서는 알 수 없습니다. 출처가 남아 있으면 "핸드오프 값이니 디자인을 확인해야 한다"와 "값이 없어 내가 정한 것이니 바꿔도 된다"가 구분됩니다. 시간이 지나 직접 짠 코드를 다시 볼 때 특히 필요했습니다.

**파생 값은 계산해서 쓴다**

`alpha()` 헬퍼로 원본 토큰에서 투명도를 계산합니다. 반투명 색을 별도 상수로 박아두지 않아, 브랜드 색이 바뀌면 파생 색이 함께 따라옵니다.

## 4. 기획 → 코드 구조: 캐릭터 성격 3종

마스코트의 성격 3종(친근형 / 엄격형 / 차분형)이라는 기획을, 화면 곳곳에 흩어진 문구가 아니라 **하나의 문구 리소스 테이블**로 구현했습니다.

- `src/copy/persona.ts` — 8개 상황 × 3개 성격의 문구를 함수 테이블로 관리
- 규칙: 하드코딩 카피 대신 이 테이블을 통해서만 참조
- 값이 들어가는 문구는 함수로 — `(v: { remainKcal }) => ...`

함수로 둔 덕분에 성격별로 **문장 구조 자체가 달라질 수 있습니다.** 같은 상황에서 친근형은 남은 물 양을 먼저 말하고 엄격형은 초과한 칼로리를 먼저 말합니다. 말투만 바꾸는 치환이었다면 문자열 테이블로 충분했겠지만, 성격마다 **무엇을 먼저 말할지**가 달라야 한다고 봤기 때문에 함수 테이블이 됐습니다.

## 5. 상태 설계와 스키마 마이그레이션

`src/store/useAppStore.ts` — Zustand + AsyncStorage 영속화. 기기에 저장된 상태가 앱 업데이트 이후에도 깨지지 않도록 **버전 마이그레이션**을 두었습니다. 현재 v5입니다.

| 버전 | 이관 내용 |
|------|-----------|
| v2 | 홈 카드 기본 순서 변경. 사용자가 순서를 직접 바꾼 적이 없을 때만 새 순서로 옮김 |
| v3 | 한글 라벨 저장 → 코드값(`"당뇨"` → `diabetes`), 목록에 없는 직접 입력값은 `custom*` 배열로 분리 |
| v4 | 끼니·증상 코드화, 음식 양을 `"1공기 210g × 2"` 문자열 → 숫자 + 단위 |
| v5 | 앱 시작일 추가. 기존 사용자는 기록이 남은 가장 오래된 날짜로 채움 |

v2가 필요했던 이유가 이 설계의 요지입니다. 기본값을 바꾼다는 것은 **이미 그 값을 쓰고 있는 사용자가 있다**는 뜻이고, 그 사람이 직접 설정한 순서를 덮어쓰면 안 됩니다. 그래서 "이전 기본값 그대로일 때만" 이동시킵니다.

**마이그레이션에서 겪은 문제**

변환 함수가 예외를 던지면 persist가 복구를 **통째로 포기합니다.** 화면에는 기록이 전부 사라지고 앱이 초기화된 것처럼 보입니다. 저장본의 버전과 실제 구조가 어긋난 상태에서 이미 변환된 값을 다시 변환하려다 발생했습니다.

지금은 이미 변환된 형태가 들어와도 그대로 통과시키는 가드를 두었습니다. 마이그레이션은 한 번 깨지면 사용자가 되돌릴 방법이 없는 자리라 방어적으로 작성해야 한다고 판단했습니다.

**날짜별 기록 구조**

`dailyRecords`는 `"2026-09-17"` 형태의 날짜 키 맵입니다. 배열로 두면 날짜를 찾을 때마다 순회해야 하고, 같은 날짜 레코드가 둘 생길 여지가 있습니다. 조회 함수는 기록이 없는 날짜에 빈 레코드를 돌려주어, 호출부마다 null 체크를 반복하지 않게 했습니다.

## 6. 인터랙션 구현

**물 섭취 카드 — 제스처 입력** (`src/screens/home/cards/WaterCard.tsx`)

- 세로 드래그로 증감. 위로 끌면 증가, 아래로 끌면 감소
- 약 4px당 50ml, **50ml 단위로 스냅** — 손가락 움직임이 정확할 수 없다는 전제
- Gesture Handler의 worklet에서 계산하고 `runOnJS`로 상태 반영
- 탭(컵), 버튼(+250ml), 되돌리기까지 **같은 동작에 세 가지 진입로**

**캐릭터가 물 섭취량에 반응** (`src/components/FittoCharacter.tsx`)

- 섭취량/목표 비율을 5단계로 구분 (바싹 마름 / 목마름 / 보통 / 촉촉 / 완전 만족)
- 단계별로 크기(0.9 → 1.06)와 **부유 애니메이션 주기**가 달라짐 — 0단계는 멈추고, 4단계는 3.2초 주기로 가장 활발
- "물을 안 마시면 캐릭터가 축 처진다"를 색이 아니라 **움직임의 속도**로 표현

## 7. 플랫폼 제약과 우회

원본 웹 프로토타입은 캐릭터의 5단계 상태를 CSS `filter`(grayscale / saturate / brightness)로 표현했지만, **React Native의 `Image`에는 CSS filter를 적용할 수 없습니다.**

선택한 해법 — 반투명 오버레이 3겹으로 근사:

| 원본 filter | 대체 |
|---|---|
| 채도 감소 | 회색 레이어 불투명도 `grayscale * 0.55` |
| 채도 증가 | 브랜드 블루 레이어 `(saturate - 1) * 0.28` |
| 밝기 | 흰색 레이어 `(brightness - 1) * 0.5` |

**중요한 건 그 다음입니다.** 코드에 "최종 5단계 일러스트가 준비되면 이미지 스왑으로 교체 권장"을 남기고, 오버레이 색 토큰에도 "이미지 스왑으로 바뀌면서 함께 제거된다"를 적었습니다.

근사치로 간 이유는 지금 필요한 것이 *정확한 색 변환*이 아니라 *단계가 구분되는 시각적 피드백*이었기 때문입니다. 다만 근사라는 사실과 더 나은 해법을 남기지 않으면, 나중에 이 코드를 보는 사람은 이게 최선인 줄 알고 그대로 둡니다. 1인 개발에서는 그 "나중에 보는 사람"이 대부분 자신입니다.

같은 맥락의 다른 사례:

- 반폭 카드에서 원본의 가로 배치(컵+컨트롤)가 45px로 찌그러져 세로 배치로 변경. 원본을 따르지 않기로 한 판단과 이유를 주석으로 남김
- 웹에서 `absoluteFill`에 width/height가 없어 이미지가 원본 크기(578×731)로 삐져나오는 문제를 크기 명시로 해결

## 8. 트러블슈팅

### 온보딩 태그를 빠르게 두 번 누르면 앞선 선택이 사라지는 문제

- **증상** 태그 선택 화면에서 두 개를 빠르게 연속으로 누르면 먼저 누른 것이 선택 해제됨
- **원인** 선택 배열 전체를 인자로 받아 갱신하는 구조라, 리렌더 전에 두 번째 클릭이 들어오면 **갱신 전의 낡은 배열**을 기준으로 덮어씀
- **해결** `toggleObTag(key, value)` — 배열이 아니라 **바뀐 항목 하나만** 받고, 스토어 내부에서 항상 최신 상태를 기준으로 토글
- **파일** `src/store/useAppStore.ts`

### 한 DB에서는 통과하고 다른 DB에서는 테이블이 안 만들어진 문제

- **증상** Postgres에 실제 요청을 보내 가입·기록·조회를 모두 확인한 뒤, 같은 흐름을 H2로 돌리는 통합 테스트를 작성했더니 9개가 한꺼번에 실패
- **원인** 직접 입력 목록 테이블의 컬럼 이름이 `value`였다. Postgres에서는 쓸 수 있지만 **H2에서는 예약어**라 `create table`이 실패했다. Hibernate는 테이블 생성 실패를 경고로만 남기고 진행하기 때문에, 부팅은 정상이었고 `insert` 시점에야 `Table not found`로 드러났다
- **해결** 컬럼 이름을 `item`으로 변경. 같은 부류인 `@OrderColumn(name = "position")`도 `sort_order`로 함께 변경
- **남긴 것** 엔티티 주석에 왜 `value`를 못 쓰는지와 어떻게 발견했는지 기록

수동 확인만 했다면 "잘 된다"로 끝났을 문제다. 테스트 DB를 운영과 다르게 잡은 것이 오히려 **DB에 종속된 코드를 드러내는 장치**가 됐다.

### Spring Boot 4로 올리면서 겪은 것들

최신 정식 버전을 골랐더니 인터넷 예제가 대부분 3.x 기준이라 그대로 쓸 수 없는 지점이 반복해서 나왔다.

| 항목 | 3.x | 4.x |
|---|---|---|
| 웹 스타터 | `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| Jackson 패키지 | `com.fasterxml.jackson.databind` | `tools.jackson.databind` |
| MockMvc 자동설정 | `...test.autoconfigure.web.servlet` | `...webmvc.test.autoconfigure` |
| enum 직렬화 설정 | `spring.jackson.serialization.*` | `spring.jackson.datatype.enum.*` |

문제를 푼 방식은 매번 같았다 — 검색해서 나오는 답이 안 맞으면 **의존성 jar 안을 직접 열어 실제 클래스 경로를 확인**했다. 예제가 없는 버전을 쓸 때는 이 방법이 가장 빠르다.

### 운동 기록만 계속 500으로 실패한 문제

- **증상** 앱에서 기록한 물은 서버에 저장되는데 운동만 `500 INTERNAL_ERROR`. 재시도 5회 후 버려짐
- **원인** 앱이 만드는 기록 ID가 `${Date.now()}` 문자열이었다. 서버는 UUID만 받으므로(명세 0-2) 요청 본문을 읽는 단계에서 실패했다. 물은 ID 없이 날짜로만 저장하는 API라 영향이 없었다
- **왜 늦게 찾았나** 서버가 이 상황에 `500`을 주고 있었다. 500은 "서버가 깨졌다"는 뜻이라 서버 로그부터 뒤지게 만든다. 실제로는 보낸 쪽 잘못이었다
- **해결** 세 가지를 함께 고쳤다
  1. UUID v4 생성기를 만들고 ID 생성 지점 9곳 교체
  2. persist 마이그레이션(v6)으로 **이미 저장된 옛 ID도 변환** — 안 하면 기존 기록이 영영 안 올라간다
  3. 서버가 요청 본문을 못 읽는 경우를 `400`으로 응답하도록 수정
- **남긴 것** 3번이 핵심 수정이다. 클라이언트 잘못을 서버 오류로 감추면 원인이 엉뚱한 곳에서 찾아진다

### PATCH에서 "안 보낸 필드"와 "null"을 구분하지 못한 문제

- **증상** 프로필 수정 API에서 물 목표 직접 설정을 해제하는 규칙을 `waterGoal: null`로 정했는데, 서버에서 "필드를 안 보낸 경우"와 구분할 방법이 없었다
- **원인** JSON에는 "값이 없음"을 나타내는 방법이 `null` 하나뿐이다. Java DTO로 역직렬화하면 두 경우 모두 필드가 `null`이 된다. `Optional<Integer>`로 감싸 세 상태를 만들어보려 했지만, Jackson은 **필드가 아예 없어도 `Optional.empty()`를 만들어서** 결국 구분되지 않았다
- **위험** 이 상태로 `null = 지우기`를 유지하면, 앱이 실수로 빠뜨린 필드가 "지워라"로 해석돼 프로필이 지워진다
- **해결** 우회 구현(커스텀 Deserializer, 추가 라이브러리) 대신 **API 계약을 바꿨다.** `null`은 안전한 쪽(유지)으로 해석하고, 지우려는 의도는 `waterGoalCustom: false`라는 명시적 필드로 받는다. 이 필드는 이미 User 응답에 있던 것이라 새 개념도 아니다
- **남긴 것** 이 세 상태가 실제로 어떻게 동작하는지 확인하는 테스트. 처음 가정이 틀렸던 자리라 가정을 코드로 고정해두었다

### 저장된 데이터를 복구하다 앱이 초기화된 것처럼 보이는 문제

- **증상** 앱을 켜면 온보딩 화면부터 다시 시작. 저장소에는 기록이 그대로 남아 있음
- **원인** persist 마이그레이션 함수가 예외를 던지면 복구 전체를 포기하고 초기 상태로 시작. 이미 코드값으로 변환된 데이터를 다시 변환하려다 타입이 맞지 않아 예외 발생
- **해결** 변환 함수가 이미 변환된 형태를 받아도 그대로 통과시키도록 가드 추가
- **파일** `src/store/useAppStore.ts`

## 9. 프론트 우선 구현과 데이터 경계 설계

화면과 인터랙션을 먼저 완성하는 순서로 진행했습니다. 그래서 데이터는 아직 일부가 목데이터지만, **연동 지점을 처음부터 한 곳씩 격리하고 각각이 어떤 소스로 교체될지 코드에 명시**했습니다.

| 위치 | 현재 | 교체 대상 |
|---|---|---|
| `screens/home/mockData.ts` | 지난 6일 걸음 수 | 건강 API |
| `HealthScreen`의 `sittingHours` | 고정값 6.5h | 기기 센서 |
| `data/foods.ts` | 로컬 음식 목록 | 식품영양성분 API |
| `utils/periodMock.ts` | 생성된 주기 데이터 | 사용자 입력 기록 |

각 지점에 "실제 데이터 소스 연동 전까지", "기기 센서 연동 전 예시값" 형태의 주석을 달아 연동 시 무엇을 건드려야 하는지가 코드에서 바로 보이게 했습니다. UI 컴포넌트는 데이터의 출처를 모르고 형태만 알기 때문에, 소스가 바뀌어도 화면 코드는 그대로입니다.

**화면을 먼저 만든 이유**

기록 앱에서 가장 불확실한 부분은 데이터 구조가 아니라 "이 화면을 매일 열게 되는가"였습니다. 그 답은 화면을 만들어 써봐야 나옵니다. 다만 이 순서에는 함정이 있습니다. 목데이터로 화면을 완성하면 화면이 목데이터의 형태에 맞춰 굳고, 나중에 실제 소스를 붙일 때 화면까지 다시 고치게 됩니다. 경계를 먼저 그어둔 이유가 그것입니다.

## 10. 앱과 서버 사이의 계약

서버 코드를 짜기 전에 **API 명세서를 먼저 작성**했고, 한 번 개정해 v1.1까지 갔습니다. v1.0에서 고친 것들:

| 항목 | v1.0 | v1.1 | 이유 |
|---|---|---|---|
| 식사 메모 | 음식 단위 | 날짜 + 끼니 단위 | 원래 구조로는 "오늘 아침 메모"를 저장할 곳이 없었음 |
| 수분 기록 | 누적 POST | 절댓값 PUT | 네트워크 재시도로 같은 값이 두 번 더해짐 |
| 음식 양 | `"1공기 210g × 2"` 문자열 | 숫자 + 단위 | 문자열은 계산도 검증도 불가 |
| 활동량 | 숫자 계수 `1.375` | 코드 `light` | 계수를 조정하면 저장된 데이터가 전부 어긋남 |

이 결함들을 **구현 전에 발견한 것**이 가장 큰 소득이었습니다. 다 만든 뒤에 알았다면 앱·서버·DB를 동시에 고쳐야 했습니다.

**게스트 모드 — 회원가입을 강제하지 않는다**

가입 없이 모든 기능을 쓰고 기록은 기기에 저장합니다. 가입하면 기기 기록을 한 번에 서버로 올립니다(`POST /me/import`).

기록 앱은 첫날 한 줄을 남기게 만드는 것이 전부입니다. 시작하자마자 회원가입 화면이 뜨면 그 전에 이탈합니다. 설계상의 이득도 있었습니다. 가입이 "기능을 여는 열쇠"가 아니라 "저장 위치를 옮기는 스위치"가 되면서 **로그인 가드가 통째로 사라졌습니다.** 앱의 가드는 온보딩 완료 여부 하나뿐입니다.

**클라이언트가 ID를 만든다**

기록의 ID(UUID)를 앱이 만들어 보내고, 서버는 처음 보는 ID면 생성하고 이미 있으면 기존 것을 돌려줍니다. 앱은 버튼을 누르는 즉시 화면에 반영하고 오프라인에서도 기록을 만듭니다. 클라이언트 ID를 쓰면 동기화할 때 임시 ID를 바꿔치기할 필요가 없고, 재시도로 같은 기록이 두 번 생기지 않습니다.

**계산은 서버가 기준**

목표 칼로리·물 목표·운동 소모 칼로리는 서버 값이 최종값입니다. 앱에도 같은 공식이 있지만 게스트 모드용이자 저장 전 미리보기용입니다. 공식이 두 곳에 있으면 언젠가 어긋나므로, 명세의 예시 값(여성 26세 165cm 55kg → 1424kcal / 1800ml)을 **양쪽 테스트에 같이 박아두었습니다.** 한쪽을 고치면 다른 쪽 테스트가 깨집니다.

## 11. 서버 구현에서의 판단

**인증** — access 30분 + refresh 14일. refresh는 갱신할 때마다 새로 발급하고(로테이션), 이미 쓴 토큰이 다시 오면 탈취로 보고 그 사용자의 토큰을 전부 폐기합니다. 토큰은 원본이 아니라 해시로 저장해 DB가 유출돼도 그 값으로 갱신할 수 없게 했습니다.

**로그인 응답을 갈라놓지 않음** — 계정이 없을 때와 비밀번호가 틀렸을 때 같은 메시지를 줍니다. 응답이 다르면 특정 이메일의 가입 여부를 확인하는 통로가 됩니다.

**에러 응답 한 모양** — 모든 실패가 `{ status, code, message }`로 나갑니다. `code`로 앱이 분기하고, `message`는 그대로 화면에 띄울 수 있는 문장입니다. 앱이 에러 코드마다 문구를 따로 관리하지 않아도 됩니다.

**패키지는 도메인별로** — 계층별(controller/service/repository)로 나누면 기능 하나를 고칠 때 폴더 세 개를 오갑니다. 도메인별로 두면 한 폴더 안에서 끝납니다.

**멱등 처리 — 같은 ID로 다시 오면 201이 아니라 200** — 기록의 ID를 앱이 만들어 보내므로, 이미 있는 ID면 새로 만들지 않고 기존 기록을 돌려줍니다. 오프라인에서 만든 기록을 재시도해도 중복이 생기지 않습니다. 다른 사용자가 쓰는 ID면 `409`입니다.

**조회 단계에서 소유자를 함께 본다** — `findByIdAndUserId(id, userId)` 형태로만 조회합니다. `findById`로 가져와 나중에 소유자를 비교하는 방식은 비교를 한 번 빼먹으면 그대로 구멍이 됩니다. 조회 자체에 넣으면 빼먹을 수가 없습니다.

**계산할 근거가 없으면 거절한다** — 목록에 없는 운동인데 앱이 칼로리도 안 보냈으면 `400`을 줍니다. 0으로 저장하면 사용자가 "0kcal 소모"를 사실로 믿게 됩니다. 앱에서 "추정값을 사실처럼 보여주지 않는다"고 정한 것과 같은 원칙입니다.

**게스트 데이터 이전은 서버 값이 이긴다** — 가입할 때 기기 기록을 올리면, ID가 겹치는 기록은 건너뛰고 날짜가 겹치는 기록은 서버 값을 유지합니다. 다른 기기에서 쓰던 기록을 오래 방치된 기기의 값으로 덮어쓰는 쪽이 더 큰 사고이기 때문입니다. 전체가 한 트랜잭션이라 중간에 실패하면 아무것도 저장되지 않습니다.

## 12. 앱과 서버를 잇는 방식 — 로컬 우선과 대기열

처음 계획은 서버 상태 캐싱 라이브러리(TanStack Query)를 넣는 것이었습니다. 코드를 보고 방향을 바꿨습니다.

그걸 도입하면 **화면 20개가 전부 서버 캐시를 읽도록 다시 쓰여야** 했습니다. 지금 모든 화면이 기기 저장소(zustand)를 보고 그리고 있으니까요. 그런데 실제로 풀어야 할 문제는 "화면이 어디서 데이터를 읽는가"가 아니라 **"기록이 서버까지 도달하는가"** 였습니다.

그래서 화면은 그대로 두고 뒤에 대기열을 놓았습니다.

```
버튼 누름 → 기기 저장소 반영(화면은 여기만 본다) → 대기열에 적재 → 순서대로 전송
```

**이 구조가 자동으로 해결한 것들**

| 보통 따로 구현하는 것 | 이 구조에서 |
|---|---|
| 낙관적 업데이트 | 화면이 이미 로컬을 보므로 공짜. 되돌리기 로직도 불필요 |
| 오프라인 지원 | 기본 동작. 대기열을 기기에 저장해 앱을 껐다 켜도 남음 |
| 화면 수정 | 한 줄도 안 고침. 스토어 액션 안에서만 대기열에 넣음 |

**대기열에 값을 넣지 않았습니다**

"무엇이 바뀌었는지"만 적고, 보낼 때 저장소에서 최신 값을 읽습니다. 물을 다섯 번 누르면 대기열에는 한 건만 남고 마지막 값 한 번만 올라갑니다. 값을 그대로 담았다면 다섯 번 보냈을 겁니다.

**순서대로 하나씩 보냅니다**

병렬이 빠르지만 "추가 → 삭제"가 뒤집혀 도착하면 지운 기록이 되살아납니다. 기록 앱에서 그 위험이 속도보다 크다고 봤습니다.

**실패를 세 가지로 나눴습니다**

연결이 없을 때는 실패로 세지 않고 대기열을 유지합니다. 비행기 모드가 길어졌다고 기록을 버리면 안 되니까요. `401`은 토큰을 갱신해 같은 작업을 다시 보냅니다. 서버가 거절한 요청은 횟수를 세고 5회를 넘기면 버립니다 — **고칠 수 없는 요청 하나가 뒤의 기록을 영영 막지 않게** 하려는 규칙입니다. 실제로 운동 기록이 500으로 실패하는 동안에도 물 기록은 정상적으로 올라갔습니다.

**내려받기는 올리기 뒤에만**

순서를 바꾸면 아직 못 올린 기록이 서버 값으로 덮여 사라집니다. 내려받기 함수 안에서도 대기열이 비어 있는지 한 번 더 확인합니다. 그리고 **서버가 준 날짜만** 덮어씁니다 — 서버에 없는 날짜의 기기 기록은 아직 못 올린 것일 수 있어서 건드리지 않습니다.

**무한 반복을 막은 지점**

처음에는 서버에서 받은 프로필을 `setProfile`로 넣었는데, 그 액션이 대기열에 쌓는 구조라 **받은 값을 다시 올려보내고 또 받는** 순환이 생겼습니다. 서버 값 반영 전용 액션을 따로 만들어 이 경로는 대기열을 건드리지 않게 했습니다.
